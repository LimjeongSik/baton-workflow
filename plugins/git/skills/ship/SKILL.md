# 커밋 & 푸시

**이 스킬을 실행한다는 것은 커밋과 푸시를 승인했다는 뜻이다.** 단계마다 확인을 받지 말고 진행한다. 다만 아래 "하드 스톱" 조건에서는 반드시 멈추고 사용자에게 묻는다.
인자로 `--no-push`를 받았으면 커밋까지만 한다.

## 1. 상태 파악

```bash
git status --short --untracked-files=all
git diff --stat && git diff --cached --stat
git log --oneline -10
```

- 변경이 없으면 커밋하지 않고 그대로 보고한 뒤 끝낸다.
- untracked 파일이 있으면 **`.gitignore`에 넣어야 할 대상인지 먼저 판단한다.** 빌드 산출물·로컬 설정·시크릿이면 커밋하지 말고 `.gitignore`에 추가할지 제안한다.
- 무엇이 바뀌었는지 모르는 상태로 커밋하지 않는다. `git diff`를 실제로 읽는다.
- `git log`로 이 저장소의 커밋 메시지 관례(언어, 형식, prefix)를 파악한다.

## 2. 사전 검사 (실패하면 커밋하지 않는다)

검사 명령은 `CLAUDE.md` / `AGENTS.md`에 적힌 명령 → `package.json` 스크립트(lockfile로 패키지 매니저 판단) → 표준 도구 순서로 찾는다. 명령을 지어내지 않는다. 검사 도구가 하나도 없으면 그 사실을 보고에 적고 넘어간다.

```bash
<lint> && <typecheck>
```

실패하면 커밋하지 않는다. 실패 내용을 보고하고, 고칠지 묻는다. `--no-verify`나 검사 우회는 하지 않는다.

프로젝트에 진행 문서(`docs/PROGRESS.md` 등)가 있으면 이번 변경이 반영됐는지 확인한다. 반영되지 않았으면 먼저 갱신한다. `progress:update` 스킬을 쓸 수 있으면 그 스킬로 갱신한다.

## 3. 보안 감사 (리뷰보다 먼저)

**소스·설정 변경이 있고** `security` 플러그인을 쓸 수 있으면 감사한다. 문서·에셋만 바뀌었으면 건너뛴다.

- 메인 에이전트라면 `security:auditor` 서브에이전트에게 맡긴다.
- Agent 툴을 쓸 수 없는 환경(서브에이전트 안)이라면 `security:audit` 스킬을 직접 호출해 수행한다.
- 플러그인이 없으면 최소한 다음은 직접 확인한다: 추적 중인 시크릿 파일, diff에 박힌 키·토큰 값.

감사는 **지적만 한다. 판단과 수정은 여기서 한다.** 각 지적의 파일·라인을 직접 Read해서 검증하고 타당한 것만 반영한다. **`critical`/`high`를 기각하려면 왜 악용될 수 없는지 코드로 보여야 한다.**

**하드 스톱:** 커밋하지 말고 사용자에게 물을 상황
- `critical`이 하나라도 남아 있을 때
- 시크릿 파일이 **이미 추적 중**일 때. `.gitignore`에 추가해도 이력에서는 사라지지 않는다. 키 폐기와 이력 정리가 필요하므로 사용자가 판단해야 한다
- `high`가 "보류"로 남았을 때

수정했으면 2단계 검사를 다시 통과시킨 뒤 넘어간다.

## 4. 코드 리뷰 (커밋 전, 소스 변경이 있고 review 플러그인을 쓸 수 있을 때)

**리뷰를 통과하기 전에는 커밋하지 않는다.** review 플러그인이 설치되어 있으면 리뷰를 통과하지 않은 소스 변경의 `git commit`/`git push`는 훅이 막는다.

`review:codex` 스킬로 커밋되지 않은 변경을 리뷰받는다. 각 지적을 코드로 검증해 타당한 것만 반영하고, 스킬이 리뷰 통과를 기록한다.

건너뛰는 경우:
- 변경이 문서·에셋·도구 설정뿐일 때 (게이트도 이런 파일은 검사하지 않는다)
- **이번 작업에서 이미 review:codex로 리뷰를 통과했고, 그 뒤로 소스를 고치지 않았을 때**
- review 플러그인이 없을 때. 이때는 보고에 "외부 리뷰 생략"이라고 적는다

리뷰 반영으로 소스가 바뀌었으면 2단계 검사를 다시 통과시킨다.

**하드 스톱:** 커밋하지 말고 사용자에게 물을 상황
- `critical` 또는 `high` 지적이 "보류"로 남아 있을 때
- 리뷰 지적을 반영한 뒤 검사가 깨졌고 고치지 못했을 때
- codex 실행 자체가 실패했을 때. 리뷰 없이 커밋할지는 사용자가 정한다. 실패를 "통과"로 취급하지 않는다. 사용자가 리뷰 없이 진행하라고 하면 review:codex 스킬의 "리뷰 생략" 절차로 기록한 뒤 진행한다

기각한 지적만 남았다면 그대로 진행하되, **기각 근거를 보고에 적는다.**

**커밋이 리뷰 게이트에 막히면** 리뷰 뒤에 소스가 바뀐 것이다. 막힌 파일을 다시 리뷰받는다. 게이트를 피하려고 명령을 바꿔 쓰거나 생략 기록을 쓰지 않는다.

## 5. 커밋 분할

성격이 다른 변경이 섞여 있으면 나눈다. 예를 들어 기능 구현, 설정 변경, 문서 갱신이 함께 있으면 커밋 3개로 나눈다.

- 경로를 명시해서 스테이징한다 (`git add src/...`). `git add .`은 변경 전체가 한 덩어리일 때만 쓴다.
- 각 커밋은 그 자체로 검사를 통과하는 상태여야 한다.
- 리뷰를 통과한 변경은 나눠서 커밋해도 게이트를 다시 거치지 않는다. 나누는 과정에서 소스를 고치면 그 파일은 다시 리뷰 대상이 된다.

## 6. 커밋 메시지

저장소의 기존 관례를 따른다. 관례가 없으면 Conventional Commits에 한국어 요약을 쓴다:

```
<type>: <요약 50자 이내>

- 변경 내용
```

`type`: `feat`(기능) `fix`(버그) `docs`(문서) `refactor`(리팩터링) `style`(포맷) `test`(테스트) `chore`(설정·빌드·도구) `build`(의존성) `perf`(성능)

- 요약에는 "무엇을 했는지"보다 **"무엇이 달라지는지"**를 쓴다. `feat: HomeScreen 추가`보다 `feat: 홈 화면에 자산 목록 표시`가 낫다.
- 본문에는 diff를 읽으면 아는 내용 말고 **판단 근거**를 적는다. 변경이 자명하면 본문을 생략한다.
- Co-Authored-By 같은 attribution은 Claude Code의 현재 설정을 따른다.
- 여러 줄 메시지는 heredoc으로 넘긴다:
  ```bash
  git commit -F - <<'EOF'
  feat: ...
  EOF
  ```

## 7. 푸시

```bash
git rev-parse --abbrev-ref HEAD
git push
```

- upstream이 없으면 `git push -u origin <현재 브랜치>`로 푸시한다.
- 푸시도 리뷰 게이트를 거친다. 원격에 없는 커밋 중 리뷰를 통과하지 않은 소스 내용이 있으면 막힌다. 막히면 4단계로 돌아가 그 커밋 범위를 리뷰받는다.
- 현재 브랜치가 기본 브랜치(`main`/`master`)인데, 저장소 관례가 PR 흐름이면(`CONTRIBUTING.md`, PR 템플릿, 기존 머지 커밋 패턴으로 판단) 푸시하기 전에 브랜치를 분리해 PR로 올릴지 묻는다. 직접 푸시가 기존 흐름이면 그대로 진행한다.

## 8. 보고

커밋 해시(짧은 형식)와 제목, 푸시한 브랜치, 검사 결과, 보안 감사·리뷰에서 채택/기각한 지적을 적는다. 여러 커밋으로 나눴으면 전부 나열한다.

## 하드 스톱: 멈추고 물어볼 것

- 사전 검사 실패
- 보안 감사 미통과: `critical` 잔존, `high` 보류, 추적 중인 시크릿 파일 발견
- 리뷰 미통과: `critical`/`high`가 보류로 남음, 반영 후 검사 실패, codex 실행 실패
- 원격이 앞서 있어 non-fast-forward로 `git push`가 거부됨. pull/rebase 여부는 사용자가 정한다
- force push가 필요한 상황. **요청 없이 절대 하지 않는다**
- 이력 재작성(`rebase -i`, 푸시된 커밋의 `--amend`), 태그 삭제, 브랜치 삭제

## 하지 않을 것

- 검사를 건너뛰거나 `--no-verify`로 우회하기
- diff를 읽지 않고 커밋하기
- 사용자가 만들지 않은 변경(다른 도구가 남긴 것)을 확인 없이 함께 커밋하기
- 커밋 메시지에 실제로 하지 않은 작업 적기
