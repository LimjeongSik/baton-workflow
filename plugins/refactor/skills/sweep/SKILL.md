# 리팩터링: 정찰 → 판별 → 실행

**순서를 건너뛰지 않는다.** 정찰 없이 고치기 시작하지 않고, 판별 없이 정찰 결과를 그대로 실행하지 않는다.
**판단은 메인 에이전트가 한다.** 정찰은 후보를 낼 뿐이고, 지적됐다는 이유만으로 고치지 않는다.

성공 조건은 하나다. **밖에서 본 동작이 그대로일 것.** 화면·요청·저장값·실패 처리·호출 순서가 전부 같아야 한다.

사용자 요청: `$ARGUMENTS` (비어 있으면 저장소 전체가 대상이다)

## 0. 기준선: 여기서 숫자를 잡아 두지 않으면 나중에 "같음"을 증명할 수 없다

```bash
git status --short --untracked-files=all
```

- **작업 트리가 지저분하면 멈추고 사용자에게 묻는다.** 리팩터링 diff와 기존 변경이 섞이면 되돌릴 수 없다.

### 프로젝트 파악

- 루트 `CLAUDE.md` / `AGENTS.md`, 진행·결정 문서(`docs/PROGRESS.md`, ADR 등)가 있으면 읽는다. 판별 단계에서 기준이 된다.
- **검사 명령을 정한다.** 우선순위는 다음과 같다:
  1. `CLAUDE.md` / `AGENTS.md`에 적힌 명령
  2. `package.json`의 `scripts`(lint/check, typecheck, test). 패키지 매니저는 lockfile로 판단하고, TypeScript인데 typecheck 스크립트가 없으면 `tsc --noEmit`을 쓴다.
  3. `Makefile`, `pyproject.toml`, `cargo`, `go` 표준 명령
  
  명령을 지어내지 않는다. 테스트 명령이 없으면 그 사실을 사용자에게 알린다. 테스트 없이 하는 리팩터링은 동작 보존을 증명할 수 없으므로, 진행 여부를 묻는다.

기준선을 돌린다:

```bash
<lint> && <typecheck> && <test> 2>&1 | tail -20
```

- 기준선이 이미 실패하면 리팩터링을 시작하지 않고 먼저 알린다.
- **테스트 스위트 수와 케이스 수를 적어 둔다.** 마지막에 이 숫자가 그대로여야 한다.

## 1. 정찰: `refactor:scout` 병렬 스폰

### 범위 나누기

소스 분포를 먼저 본다:

```bash
git ls-files | awk -F/ 'NF>2{print $1"/"$2} NF==2{print $1} NF==1{print "(root)"}' | sort | uniq -c | sort -rn | head -40
```

- 생성물·벤더·빌드 산출물·lockfile·에셋·테스트 fixture는 범위에서 뺀다.
- 남은 소스를 **겹치지 않는 2~4개 묶음**으로 나눈다. 같은 계층끼리 묶고(UI·화면 / 컴포넌트·스타일 / 서비스·데이터·상태 / 공용 유틸·타입·설정·루트), 파일 수가 대략 비슷하게 맞춘다. 범위가 겹치면 같은 항목이 중복으로 올라온다.
- 소스 파일이 대략 80개 이하로 작은 프로젝트면 스카우트 하나로 충분하다.
- 사용자가 범위를 좁혀 요청했으면(예: "결제 화면만") **그 범위만 스카우트 하나로** 돌린다. 기계적으로 여러 개를 띄우지 않는다.

### 스폰

스카우트들을 **한 메시지에서 동시에** 띄운다 (`subagent_type: "refactor:scout"`).
각 프롬프트에 넣을 것: **담당 범위(경로 목록)**, 사용자가 지정한 초점(있으면), 그리고 "코드를 고치지 말고 후보만 낼 것".

- 스카우트가 후보를 하나도 내지 못했으면 그 범위는 비워 둔다. 다시 시켜서 채우지 않는다.

## 2. 판별: 메인이 코드로 검증한다

올라온 후보를 **그대로 믿지 않는다.** 하나씩 해당 파일을 직접 열어 확인한 뒤 채택/기각/보류를 정한다.

**채택** (코드로 확인된 것만):
- 루트·폴더 `CLAUDE.md`에 명시된 규칙 위반 (폴더 경계 위반, 스타일 방식 위반, 디자인 토큰 밖 하드코딩 등)
- 같은 규칙이 두 곳 이상에 복제돼 있어서, 한쪽만 고치면 어긋나는 상태
- 책임이 명백히 잘못 놓여 있어서, 옮기면 호출부가 실제로 단순해지는 것
- 실패 경로의 비일관: 에러 계약 우회, 롤백 누락
- import 검색으로 확인된 죽은 코드

**기각** (기각도 정상적인 결론이다):
- **오버엔지니어링:** 지금 필요 없는 추상화·설정 옵션·확장 지점, 쓰는 곳이 하나뿐인데 공용으로 올리자는 제안
- 파일·라인·심볼이 실제로 존재하지 않음 (환각)
- 동작이 미묘하게라도 달라지는 제안. 리팩터링이 아니라 별건이므로 **"후속 제안"으로만 보고**한다
- 진행·결정 문서에서 이미 결정된 방향을 되돌리는 것
- 네이밍·포맷 취향, 린터·포매터가 이미 잡는 것
- 미착수 영역에 대한 선제 구조 제안

**깊이가 `deep`이거나 위험이 `high`인 항목은 혼자 판별하지 않는다.** `general-purpose` 에이전트를 `model: "opus"`로 띄워 "이 변경이 현재 동작 계약을 정말 그대로 지키는가"만 따로 검증받고, 그 결과를 근거로 채택 여부를 정한다. 그 외 항목은 메인이 직접 판별한다.

**애매하면 채택하지 않는다.** 확신이 서지 않는 것은 보류로 두고 사용자에게 넘긴다.

판별이 끝나면 **실행 전에 채택 목록을 사용자에게 보여준다:**

| # | 제목 | 대상 | 등급 | 위험 | 판단 | 근거 |
|---|---|---|---|---|---|---|

`위험: high`가 하나라도 있으면 **사용자 승인을 받고 진행한다.** low/medium만 있으면 그대로 이어간다.

## 3. 실행: `refactor:applier`

- **같은 파일을 건드리는 항목은 한 에이전트에 묶어서 순차로** 넘긴다. 병렬로 띄우면 서로의 편집을 덮어쓴다.
- 파일이 겹치지 않는 묶음끼리는 병렬로 띄워도 된다.
- **위험 `high` 또는 깊이 `deep` 항목은 `model: "opus"`로 스폰한다.** 나머지는 에이전트에 정의된 모델을 그대로 쓴다.
- 프롬프트에 넣을 것: 채택 항목의 **제목·대상 파일·현재 동작 계약·제안·검증 방법**, 0단계에서 정한 **검사 명령**, 그리고 "목록 밖은 손대지 말 것".
- 기준선 테스트 숫자를 함께 넘긴다. 실행 에이전트가 그 숫자로 자기 결과를 대조한다.

**화면에 보이는 결과가 조금이라도 달라지는 항목**(간격·정렬·계층 변경 포함, 스카우트 표의 `디자인: yes`)은 실행 에이전트에게 넘기기 **전에** 메인이 처리한다. `ui:design`이 있으면 메인이 그 스킬로 목업을 만들어 사용자 승인을 받고, 승인된 목업 경로를 프롬프트에 넣는다. 없으면 `frontend-design`을 먼저 거치라고 프롬프트에 적는다.

## 4. 검증: 메인이 직접 다시 돌린다

```bash
<lint> && <typecheck> && <test> 2>&1 | tail -20
git diff --stat
```

- **테스트 스위트·케이스 수가 0단계와 같아야 한다.** 줄었으면 테스트가 지워졌거나 동작이 바뀐 것이다. 원인을 찾을 때까지 끝내지 않는다.
- `git diff`에서 **테스트 파일의 단언이 바뀐 곳이 있는지** 본다. import 경로 외의 변경이 있으면 되돌린다.
- `review:codex` 스킬을 쓸 수 있으면, 커밋하기 전에 그 스킬로 작업 트리를 리뷰받는다. 각 지적은 코드로 검증해서 타당한 것만 반영한다. 리뷰를 통과하지 않은 변경은 커밋·푸시가 막힌다. 쓸 수 없으면 보고에 "외부 리뷰 생략"이라고 적는다.

## 5. 보고

| 항목 | 등급 | 판단 | 결과 | 만진 파일 |
|---|---|---|---|---|
| 제목 | must/should/optional | 채택/기각/보류 | 완료/되돌림 | 경로 |

표 아래에 다음을 적는다:
- 기준선 대비 검사 결과. `80 suites / 879 tests → 같은 수` 형태로 **숫자를 적는다**
- **기각한 항목과 그 근거.** 반영한 것만 적지 않는다
- 보류·후속 제안. 동작이 바뀌어서 뺀 것은 여기에 이유와 함께 적는다
- 사람이 눈으로 확인해야 할 화면이 있으면 **무엇을 봐야 하는지** 적고 멈춘다. 앱·시뮬레이터는 사용자가 요청할 때만 띄운다

프로젝트에 진행 문서(`docs/PROGRESS.md` 등)가 있으면 이번 작업을 반영한다. `progress:update` 스킬을 쓸 수 있으면 그 스킬로 갱신한다.

## 하지 않을 것

- 정찰 결과를 검증 없이 일괄 실행
- 테스트를 고쳐서 통과시키기. 깨졌으면 되돌린다
- 목록 밖 개선을 끼워 넣기. 말로만 제안한다
- 동작 개선·버그 수정을 리팩터링에 섞기. 별건으로 분리해 보고한다
- 커밋·푸시. 사용자가 따로 요청할 때만 한다
