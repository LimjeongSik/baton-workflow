# Codex 리뷰 → 판단 → 반영

작업 단위를 마치면 codex에게 리뷰를 받고, **타당한 지적만 골라 반영한다.** 리뷰는 제안일 뿐이고 판단은 메인 에이전트가 한다. 지적받았다는 이유만으로 고치지 않는다. 채택한 수정은 직접 해도 되고 구현 서브에이전트에게 맡겨도 되지만, 채택과 기각은 메인 에이전트가 정한다.

## 리뷰 게이트: 리뷰 전에는 커밋·푸시할 수 없다

Claude가 실행하는 `git commit`/`git push`를 훅이 검사한다.

- **커밋:** 이번 커밋에 담기는 소스 변경(staged 파일, `git add`나 commit에 준 경로, `commit -a`)이 리뷰를 통과한 내용이어야 한다.
- **푸시:** 원격에 없는 커밋들이 바꾼 소스 파일의 HEAD 내용이 리뷰를 통과한 내용이어야 한다.
- 통과는 **파일 내용 단위**로 기록된다(6단계). 리뷰 뒤에 파일이 바뀌면 다시 리뷰해야 하고, 통과한 변경은 여러 커밋으로 나눠도 된다. 공백·줄바꿈만 바뀐 파일은 이전 통과를 이어받는다(Python·YAML처럼 공백이 의미를 갖는 파일은 제외).
- 문서·에셋·lockfile·`.claude/` 설정, merge·cherry-pick·revert·rebase 중의 커밋, 원격 브랜치 삭제는 검사하지 않는다.
- codex CLI가 없으면 막는 대신 사용자에게 확인을 받는다.
- 훅이 판단할 수 없으면 통과시키지 않는다: 입력을 해석하지 못하면 막고, git이 실패하거나 해석할 수 없는 형태(`xargs git commit` 등)면 확인을 받는다. `sh -c`, `eval`, 백틱, git alias 안의 커밋도 검사한다.
- 처음 통과를 기록하면 `.git/hooks`에 pre-commit·pre-push 백스톱을 설치한다(기존 훅이나 `core.hooksPath`가 있으면 건너뛴다). Claude Code가 실행한 커밋·푸시만 검사하고, 사람이 터미널에서 하는 커밋은 막지 않는다. 끄려면 `BATON_BACKSTOP=0`.

끄는 법(프로젝트 `.claude/settings.json`의 `env`): `REVIEW_GATE=0`(전체), `REVIEW_GATE_COMMIT=0`(커밋을 먼저 하고 나중에 리뷰하는 흐름. 푸시는 계속 막힌다), `REVIEW_GATE_PUSH=0`, `REVIEW_GATE_STOP=0`.

## 0. 사전 확인

```bash
git status --short --untracked-files=all
git log --oneline refs/codex-review/last..HEAD   # ref가 없으면 생략
```

리뷰 범위는 1단계 스크립트가 정한다(아직 리뷰하지 않은 내용만). 여기서는 변경이 있는지와 성격만 파악한다. 둘 다 비어 있으면 그대로 종료한다. 기존 프로젝트에 처음 도입해 원격에 없는 커밋이 많으면 `--base <ref>`로 범위를 좁힌다 (예: `--base origin/main`).

### 위험도에 맞춘 리뷰

변경의 위험도를 스크립트가 판정한다(`git:ship`의 `stage.mjs plan`도 같은 판정을 쓴다). 판정은 경로(인증·API·라우트·서버·미들웨어 등), 설정·의존성·배포 파일, 추가된 줄의 패턴(시크릿·토큰 저장·셸 실행·`innerHTML`·SQL·`process.env` 등), 규모(기본 소스 20줄·3개 파일 이하)로 한다.

| 위험도 | 리뷰 |
|---|---|
| trivial (작고 민감하지 않음) | codex를 부르지 않는다. `mark-passed.mjs --auto`로 자동 생략을 기록한다 (6단계) |
| standard | `review` (codex 기본 리뷰) |
| sensitive | `adversarial-review` (설계와 가정까지 의심하는 리뷰) |

`BATON_MODE` 환경 변수(프로젝트 `.claude/settings.json`의 `env`)로 조절한다: `fast`(민감하지 않으면 trivial로 본다), `standard`(trivial도 리뷰한다), `strict`(모두 sensitive로 본다). 어떤 모드도 민감한 변경을 낮추지 않는다. 사용자가 이번 리뷰의 모드를 직접 정하면 그것을 따른다.

### 품질 게이트 결정

리뷰 전에 로컬 검사부터 통과시킨다. 검사에서 걸리는 문제를 codex에게 물을 필요는 없다. 검사 명령은 다음 순서로 찾는다.

1. `CLAUDE.md` / `AGENTS.md`에 명시된 lint·typecheck·test 명령
2. `package.json`의 `scripts` 중 `lint`, `typecheck`/`type-check`, `test`. 패키지 매니저는 lockfile로 판단한다 (`bun.lock*` → bun, `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, 그 외 npm). TypeScript 프로젝트에 typecheck 스크립트가 없으면 `tsc --noEmit`을 쓴다.
3. 다른 생태계의 표준 명령 (`Makefile`의 `lint`/`test`, `pyproject.toml`의 ruff·pytest, `cargo clippy`/`cargo test`, `go vet`/`go test ./...` 등)

검사 명령을 찾지 못하면 그 사실을 보고에 적고 넘어간다. 명령을 지어내지 않는다.

## 1. 리뷰 실행

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/run-codex.sh" $ARGUMENTS
```

- **범위를 주지 않으면 아직 리뷰하지 않은 내용만 리뷰한다.** 스크립트가 임시 worktree를 만들어, 이미 통과한 파일·줄과 공백만 바뀐 파일을 diff에서 뺀다. 미커밋 변경과 원격에 없는 커밋을 함께 다루므로 0단계의 범위 판단을 따로 하지 않아도 된다. 리뷰할 내용이 없으면 codex를 부르지 않고 "리뷰할 새 변경이 없습니다"로 끝난다. 이때는 6단계 기록만 한다.
- 재리뷰(5단계)도 같은 방식이라 반영한 수정분만 본다.
- 모드를 주지 않으면 위의 위험도 표대로 고른다. 직접 정하려면 첫 인자로 `review`나 `adversarial-review`를 준다. 포커스 텍스트는 `adversarial-review`에서만 쓸 수 있다.
- 예전처럼 작업 트리 전체를 보려면 `--full`을 준다 (작업 트리가 깨끗하면 `--base <마지막 리뷰 지점>`). 기존 프로젝트에 처음 도입하는 경우처럼 범위를 직접 정하려면 `--base <ref>`를 준다.
- 끝날 때까지 기다린다.
- Bash `timeout`은 `600000`으로 준다.
- 리뷰 원문은 stdout과 `<저장소 루트>/.claude/review-logs/<시각>-<HEAD 단축 sha>.md`에 남는다.
- 특정 관점을 강조하려면 마지막 인자로 포커스 텍스트를 붙인다 (예: `"세션 쿠키 검증 경로"`).
- 변경 규모가 크면(대략 파일 15개 또는 800줄 초과) `run_in_background: true`로 띄우고 진행 상황을 확인한다. 결과는 `/codex:status`, `/codex:result`로 조회한다.
- 종료 코드 127은 codex CLI나 플러그인 설치 문제다. 인증을 우회하려 하지 말고, 사용자에게 `/codex:setup`을 안내한 뒤 멈춘다.
- codex가 JSON 파싱 실패나 실행 실패를 보고하면 지적을 지어내지 말고, stderr의 핵심 줄만 전달한 뒤 멈춘다.

출력 형태는 `[severity] 제목 (파일:라인)` + 본문 + `Recommendation`이다.

## 2. 판단: 각 지적을 코드로 검증

리뷰 결과를 그대로 믿지 않는다. **지적마다 해당 파일·라인을 직접 읽어서 확인한 뒤** 채택과 기각을 정한다.

먼저 이 저장소의 규약 문서를 파악한다: 루트와 변경된 폴더의 `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, 그리고 그 문서들이 가리키는 스펙·설계 문서.

지적마다 아래 세 가지를 확인해 표(7단계)에 적는다. 셋 중 하나라도 채울 수 없으면 채택하지 않는다.

1. **코드 근거:** 지적한 파일·라인을 직접 읽었고, 지적한 코드가 실제로 그렇게 생겼다.
2. **재현 경로:** "어떤 입력·상태에서 → 무엇이 잘못되는가"를 한 줄로 쓸 수 있다. 가능하면 테스트나 명령으로 실제로 재현한다.
3. **심각도:** codex가 붙인 심각도를 그대로 쓰지 않고, 재현 경로의 영향(데이터 손실·보안·사용자에게 보이는 오류·내부 품질)으로 다시 매긴다.

**채택** (검증된 경우에만):
- 실제 재현 경로가 있는 버그: null/undefined, 경쟁 상태, 처리되지 않은 실패 경로, 잘못된 상태 전이
- 데이터 손실·보안·권한 문제 (인증·토큰 검증 누락 등)
- 타입 안전성 붕괴 (`any` 우회, 실제로 깨진 제네릭)
- 저장소에 명시된 규약 위반: 위 규약 문서, 폴더·파일 네이밍 컨벤션, 디자인 토큰 사용 규칙 등
- 빈 상태/로딩/에러 처리 누락 중 사용자에게 실제로 보이는 것

**기각** (기각도 정상적인 결론이다):
- 지적한 파일·라인·코드 경로가 실제로 존재하지 않음 (환각)
- 이번 변경 범위 밖의 기존 코드에 대한 지적 → 반영하지 않고 "후속 과제"로만 보고
- 이 프로젝트에 아직 없는 인프라를 전제한 지적 (스펙에 없는 계층·기능)
- 스타일·네이밍 취향, 린터가 이미 강제하는 항목
- 근거 없이 "~할 수도 있다" 수준인 추측, 또는 `confidence`가 낮고 코드로 확인되지 않는 것
- 스펙이나 프로젝트 아키텍처 방향과 충돌하는 제안

**애매하면 반영하지 않는다.** 확신이 없는 지적은 "보류"로 두고, 판단 근거와 함께 사용자에게 넘긴다.
`critical`/`high`는 반드시 코드로 검증까지 마친다. 검증 없이 기각하지 않는다. 기각할 때도 "왜 재현되지 않는가"를 코드 근거로 적는다.

### 심각도 정책

프로젝트 문서에 별도 정책이 있으면 그것을 따른다. 없으면 아래 기본값을 쓴다.

| 심각도 | 처리 |
|---|---|
| critical / high | 코드로 검증한 뒤 **사용자 확인 없이 바로 수정** → 품질 게이트 → 재리뷰 1회 |
| medium | 이번 작업 범위의 실제 결함이면 수정, 아니면 후속 과제로 보고 |
| low | 보고만 한다 |
| 환각·범위 밖·취향 | 기각 |

## 3. 반영

- 채택한 지적만, **지적한 범위 안에서 최소한으로** 수정한다.
- 리뷰가 언급하지 않은 리팩터링·정리·개선을 끼워 넣지 않는다.
- 이번 변경분 밖의 파일을 건드려야만 고칠 수 있으면, 고치기 전에 먼저 그 사실을 알린다.
- 리뷰의 `Recommendation`이 이 코드베이스에 맞지 않으면 의도(무엇을 막으려는지)만 취하고, 구현은 프로젝트 관례에 맞춘다.
- **반영분은 커밋하지 않고 둔다** (기본 델타 리뷰와 `--full` 모두). 커밋은 리뷰를 통과한 뒤 `git:ship`이나 사용자가 한다.
- 사용자가 `--base`로 이미 커밋된 범위만 리뷰하라고 했다면 반영분을 커밋한다. 커밋 메시지는 저장소 컨벤션을 따르고, 특별한 컨벤션이 없으면 `fix: codex 리뷰 반영 - <요약>`을 쓴다. 이 커밋도 6단계 기록 전에는 커밋 게이트에 걸리므로, 4단계 검증까지 마친 뒤 6단계를 먼저 하고 커밋한다.

## 4. 검증

0단계에서 정한 품질 게이트를 다시 돌려 수정 때문에 새 위반이 생기지 않았는지 확인한다. 실패하면 통과할 때까지 고친다.

## 5. 재리뷰 (조건부)

`critical` 또는 `high`를 실제로 반영한 경우에만 1회 더 돌린다. **최대 2라운드까지만 한다.**
2라운드 뒤에도 새 지적이 남으면 반영하지 말고 보고만 한 뒤 사용자 판단을 받는다. 루프를 돌지 않는다.

## 6. 리뷰 통과 기록

리뷰, 반영, 검증을 마치면 지금 내용을 리뷰 통과로 기록한다. 이 기록이 있어야 커밋·푸시 게이트가 열린다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/mark-passed.mjs" --log <이번 리뷰 로그 경로>
```

- 미커밋 소스 변경과 원격에 없는 커밋의 소스 내용을 파일별 해시로 `<git-dir>/codex-review/reviewed.json`에 기록하고, 기준점 `refs/codex-review/last`를 HEAD로 옮긴다.
- **기록한 뒤에는 소스를 고치지 않는다.** 고치면 그 파일은 다시 리뷰 대상이 된다.
- **codex 실행 자체가 실패했다면 기록하지 않는다.** 실패는 통과가 아니다.
- **보류한 `critical`/`high`가 있으면 기록하지 않는다.** 사용자가 판단한 뒤에 기록한다.

### 자동 생략 (위험도가 낮은 변경)

위험도가 trivial(또는 `BATON_MODE=fast`에서 민감하지 않은 변경)이면 codex를 부르지 않고 기록한다. 사용자 동의는 필요 없다. 스크립트가 위험도를 다시 판정해서, 맞지 않으면 기록하지 않고 종료 코드 3과 근거를 낸다. 그때는 리뷰를 실행한다.

```bash
node "${CLAUDE_SKILL_DIR}/scripts/mark-passed.mjs" --auto
```

### 리뷰 생략

리뷰가 필요 없는 변경(생성된 코드, 포맷만 바뀐 변경, 설정 값 한 줄 등)이라고 판단하면, **그 이유를 사용자에게 밝히고 동의를 받은 뒤에만** 생략으로 기록한다:

```bash
node "${CLAUDE_SKILL_DIR}/scripts/mark-passed.mjs" --skip "포매터 실행 결과만 포함"
```

사용자가 "리뷰 없이 커밋해"라고 직접 요청한 경우도 같다. 생략 이유는 기록에 남는다. 게이트를 피하려고 생략 기록을 쓰지 않는다.

### Stop 게이트

이 저장소에서 한 번이라도 리뷰를 기록하면 Stop 게이트도 켜진다. 소스를 고친 턴이 끝날 때 리뷰를 통과하지 않은 변경이 남아 있으면 이 스킬을 실행하라고 요구한다. 아직 작업 중이라 리뷰할 단계가 아니면 그 이유를 한 줄로 밝히고 끝내도 된다.

## 7. 보고

다음 표를 반드시 출력한다:

| 지적 | 심각도 (codex → 판단) | 판단 | 코드 근거 | 재현 경로 | 반영 내용 |
|---|---|---|---|---|---|
| 제목 (파일:라인) | high → medium | 반영 / 기각 / 보류 | 읽은 코드에서 확인한 것 한 줄 | 입력·상태 → 잘못된 결과 (재현 못 하면 `-`와 이유) | 수정 요약 또는 `-` |

표 아래에 다음을 적는다:
- 리뷰 범위와 모드 (스크립트가 출력한 위험도·델타 범위)
- 품질 게이트 결과 (실행한 명령과 결과). 실패했으면 숨기지 말고 그대로 적는다.
- 기각/보류한 지적 중 후속 과제로 남길 것

## 하지 않을 것

- 리뷰 지적을 검증 없이 일괄 반영하기
- 리뷰 결과를 근거로 푸시하기 (사용자가 따로 요청할 때만 한다)
- 게이트를 우회하기: `--no-verify`, 게이트를 피하려는 생략 기록, 훅이 인식하지 못하게 명령을 바꿔 쓰기
- codex 실행에 실패했을 때 리뷰 결과를 상상해서 채우기
- 리뷰가 조용히 끝났다고 "지적 없음"으로 보고하기. 실행 실패와 지적 0건은 구분해서 보고한다.
