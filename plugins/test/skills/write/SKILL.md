# 테스트 작성 & 실행

대상 코드의 동작을 테스트로 고정하고, 실제로 실행해서 결과를 보고한다. **테스트는 소스가 맞는지 확인하는 도구다. 테스트를 통과시키려고 소스를 바꾸거나 단언을 약화시키지 않는다.**

- 인자 없음: 커밋되지 않은 변경 파일이 대상이다.
- 경로: 그 파일·폴더가 대상이다. `--base <ref>`: `<ref>...HEAD`의 변경도 포함한다.

## 1. 하네스 파악

```bash
node "${CLAUDE_SKILL_DIR}/scripts/detect.mjs" $ARGUMENTS
```

출력되는 JSON의 내용:
- `runner`: 설치된 러너. 없으면 `null`이고, 그때는 `recommended`에 추천 러너가 들어 있다
- `project`: 언어, 패키지 매니저와 설치·실행 명령, 프레임워크, `testScript`, 설정 파일, 경로 별칭
- `layout`: 기존 테스트 배치와 표본 파일
- `targets`: 대상 소스 파일마다 테스트를 둘 경로(`testPath`)와 이미 있는 테스트(`existing`)

`targets`가 비었으면 테스트를 쓸 대상이 없는 것이다. 이 경우 기존 테스트만 실행하고(4단계) 보고한다.

## 2. 러너가 없으면: 묻고 설치한다

`runner`가 `null`이면 **설치하기 전에 반드시 AskUserQuestion으로 묻는다.** 묻지 않고 설치하지 않는다.

- 질문: "테스트 러너가 없습니다. `<recommended.name>`을(를) 설치한 뒤 테스트를 작성할까요?"
- 선택지: `<recommended.name>` 설치 후 진행 (Recommended) / 다른 러너 설치 후 진행 (RN이 아니면 jest, RN이면 vitest) / 설치하지 않고 테스트 생략
- 각 선택지 설명에 설치할 패키지와 바뀔 파일(`package.json`, lockfile, 설정 파일)을 적는다.

동의하면 `references/setup.md`대로 설치하고, 그 문서의 "설치 확인"까지 마친다. 설치나 확인이 실패하면 멈추고 실패 출력을 그대로 보고한다.

거절하면 테스트를 쓰지 않고 끝낸다. 보고에 "테스트 생략: 러너 없음, 사용자가 설치 거절"이라고 적는다.

## 3. 작성

### 위치: 각 폴더 하위 `__tests__/`

`targets[].testPath`가 기본 위치다. 예: `src/lib/format.ts` → `src/lib/__tests__/format.test.ts`.

- 루트나 폴더의 CLAUDE.md에 테스트 위치 규칙이 있으면 그 규칙을 따른다.
- Python은 `__tests__` 관례가 없다. 기존 배치를 따르고, 없으면 `tests/test_<모듈>.py`에 둔다. Go는 같은 폴더의 `<이름>_test.go`, Rust는 같은 파일의 `#[cfg(test)]` 모듈이다.
- `existing`에 테스트가 이미 있으면 새 파일을 만들지 않고 그 파일에 추가한다. 기존 테스트를 다른 위치로 옮기지 않는다.

### 쓰기 전에 읽는다

1. 대상 소스를 끝까지 읽는다. 공개된 동작(export된 함수, 컴포넌트 props와 사용자 상호작용, 핸들러의 입출력)을 목록으로 만든다.
2. `layout.samples`의 기존 테스트 2~3개를 읽고 import 방식, 렌더·쿼리, 비동기 처리, 목킹, 픽스처 패턴을 그대로 따른다. 라이브러리 API는 기억이 아니라 설치된 버전과 기존 테스트를 기준으로 한다.
3. 설정 파일(`project.configFiles`)에서 전역 setup과 이미 목킹된 모듈을 확인한다. 같은 모듈을 다시 목킹하면 깨질 수 있다.
4. import는 경로 별칭(`project.aliases`)이 있으면 별칭을 쓴다.

### 무엇을 테스트하나

구현 세부가 아니라 동작을 테스트한다.

- **순수 로직**(포맷터, 검증, 상태 전이, 계산): 정상값, 경계값, 잘못된 입력을 덮는다.
- **컴포넌트**: 렌더 결과와 사용자 상호작용의 결과. 접근성 쿼리(`getByRole`, `getByLabelText`)를 우선한다.
- **핸들러·API**: 성공, 실패, 빈 결과, 권한 없음 같은 주요 분기와 부수효과 호출.
- **외부 경계**(네트워크, 시간, 난수, 파일): 그 경계만 목킹한다. 테스트 대상 자체를 목킹하지 않는다.

하지 않는다:
- 스냅샷 테스트. 깨지면 무비판적으로 갱신하게 되어 회귀를 못 잡는다.
- 테스트끼리 상태 공유. 스토어, 쿼리 클라이언트, 타이머, 목은 테스트마다 새로 만들거나 되돌린다.
- 커버리지 숫자를 채우려고 의미 없는 테스트 쓰기 (getter 호출, 상수 비교 등).

## 4. 실행

1. 새로 쓴 테스트 파일만 먼저 실행한다. 예: `<runScript> test -- src/lib/__tests__/format.test.ts`. 명령은 반드시 프로젝트 스크립트(`project.testScript`)를 거친다. `bun test`처럼 런타임 내장 러너를 직접 부르면 프로젝트 설정을 건너뛸 수 있다.
2. 통과하면 전체 테스트를 실행해서 기존 테스트가 깨지지 않았는지 본다.
3. 타입 검사 스크립트가 있으면 함께 돌린다. 테스트 파일의 타입 오류도 실패다.

### 실패했을 때

먼저 테스트가 틀렸는지 소스가 틀렸는지 가린다.

- **테스트가 틀렸으면**(잘못된 셀렉터, 비동기 대기 누락, 잘못된 목) 테스트를 고친다. 단언을 약하게 바꿔서 통과시키지 않는다.
- **소스가 틀렸으면**: 소스를 고치지 않는다. 어느 파일 어느 줄이 어떤 입력에서 무엇을 잘못 내는지 근거와 함께 보고하고 멈춘다. 실패하는 테스트는 그대로 둔다. 그 테스트가 버그를 증명한다.
- 테스트 수정을 두 번 했는데도 원인을 못 가리면 멈추고 보고한다.

## 5. 보고

```
| 대상 | 테스트 파일 | 케이스 | 결과 |
|---|---|---|---|
| src/lib/format.ts | src/lib/__tests__/format.test.ts | 6 | 통과 |
```

표 아래에 다음을 적는다:
- 실행한 명령과 전체 결과(스위트·케이스 통과/실패 수)를 **실제 출력 그대로**
- 러너를 설치했으면 설치한 패키지와 바뀐 파일
- 소스 버그로 판단한 실패: 파일·라인과 근거
- 테스트를 쓰지 않은 대상과 그 이유 (예: 타입 정의만 있음, 외부 SDK 래퍼라 통합 테스트 대상)

## 하지 않을 것

- 사용자 동의 없이 러너나 테스트 라이브러리 설치하기
- 소스 로직 고치기. 테스트 작성에 꼭 필요한 export 추가도 먼저 보고하고 묻는다
- 기존 테스트 설정(전역 setup, 설정 파일)을 동의 없이 바꾸기. 러너를 새로 설치할 때 만드는 설정은 예외다
- 실패한 테스트를 `skip`·`todo`로 바꾸거나 지워서 통과시키기
- 실행하지 않고 "통과"라고 보고하기
- 커밋·푸시하기
