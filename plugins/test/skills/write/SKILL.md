# 테스트 작성 & 실행

대상 코드의 동작을 테스트로 고정하고, 실제로 실행해서 결과를 보고한다. **테스트는 소스가 맞는지 확인하는 도구다. 테스트를 통과시키려고 소스를 바꾸거나 단언을 약화시키지 않는다.**

- 인자 없음: 커밋되지 않은 변경 파일이 대상이다.
- 경로: 그 파일·폴더가 대상이다. `--base <ref>`: `<ref>...HEAD`의 변경도 포함한다.

## 1. 하네스 파악

```bash
node "${CLAUDE_SKILL_DIR}/scripts/detect.mjs" $ARGUMENTS
```

출력되는 JSON의 내용:
- `runner`: 설치된 러너. 없으면 `null`이고, 그때는 `recommended`에 추천 러너가 들어 있다
- `project`: 언어, 패키지 매니저와 설치·실행 명령, 프레임워크, `testScript`, 설정 파일, 경로 별칭
- `layout`: 기존 테스트 배치와 표본 파일
- `targets`: 대상 소스 파일마다 기본 테스트 경로(`testPath`, JS/TS는 `__tests__/`)와 이미 있는 테스트(`existing`)

이 프로젝트의 작업 방식 프로필(prefs 플러그인이 프로젝트 루트 `learn/learned.md`에 학습해 두고 세션 시작 시 넣는다)이 컨텍스트에 있으면 작업 방식·코드 패턴·피하는 것 절을 따른다. `[확정]` 항목은 묻지 않고 기본값으로 따르고, `[추정]` 항목은 다른 근거가 없을 때만 따르고 따랐으면 보고에 밝힌다. 이번 요청과 다르면 요청을 따른다.

`targets`가 비었으면 테스트를 쓸 대상이 없는 것이다. 이 경우 기존 테스트만 실행하고(4단계) 보고한다.

## 2. 러너가 없으면

`runner`가 `null`일 때:

- **사용자가 이번 요청에서 러너 설치를 이미 말했으면**(예: "vitest 깔고 테스트 써줘") 묻지 않고 그 러너를 설치한다. 러너를 지정하지 않았으면 `recommended`를 쓴다.
- **그 밖에는 설치하기 전에 AskUserQuestion으로 묻는다.** 테스트 작성 요청에는 새 도구 도입이 들어 있지 않기 때문이다.
  - 질문: "테스트 러너가 없습니다. `<recommended.name>`을(를) 설치한 뒤 테스트를 작성할까요?"
  - 선택지: `<recommended.name>` 설치 후 진행 (Recommended) / 다른 러너 설치 후 진행 (RN이 아니면 jest, RN이면 vitest) / 설치하지 않고 테스트 생략
  - 각 선택지 설명에 설치할 패키지와 바뀔 파일(`package.json`, lockfile, 설정 파일)을 적는다.

설치는 `references/setup.md`대로 하고, 그 문서의 "설치 확인"까지 마친다. 설치나 확인이 실패하면 멈추고 실패 출력을 그대로 보고한다.

거절하면 테스트를 쓰지 않고 끝낸다. 보고에 "테스트 생략: 러너 없음, 사용자가 설치 거절"이라고 적는다.

## 3. 작성

`${CLAUDE_SKILL_DIR}/references/testing-rules.md`를 읽고 따른다. 하네스 파악, 위치, 기대값의 출처, 무엇을 테스트할지, 실패했을 때의 처리가 모두 거기 있다. 1단계 출력을 이렇게 쓴다:

- **위치:** 규칙 문서 2절의 순서대로 정한다. `targets[].existing`이 있으면 그 파일에 추가한다. `layout`에서 기존 배치를 보고, 배치가 없을 때 `targets[].testPath`(JS/TS 기본값 `__tests__/`)를 쓴다.
- **읽을 것:** `layout.samples`의 기존 테스트, `project.configFiles`의 전역 setup과 목킹, `project.aliases`의 경로 별칭.
- **기대값:** 대상 소스의 공개된 동작(export된 함수, 컴포넌트 props와 사용자 상호작용, 핸들러의 입출력)을 목록으로 만든다. 사용자가 요구사항을 말했으면 그것이 먼저다.

## 4. 실행

1. 새로 쓰거나 고친 테스트 파일만 먼저 실행한다. 명령은 반드시 프로젝트 스크립트(`project.testScript`)를 거친다.
2. 통과하면 전체 테스트를 실행해서 기존 테스트가 깨지지 않았는지 본다.
3. 타입 검사 스크립트가 있으면 함께 돌린다.

실패했을 때는 규칙 문서 6절을 따른다.

## 5. 보고

```
| 대상 | 테스트 파일 | 케이스 | 결과 |
|---|---|---|---|
| src/lib/format.ts | src/lib/__tests__/format.test.ts | 6 | 통과 |
```

표 아래에 다음을 적는다:
- 실행한 명령과 전체 결과(스위트·케이스 통과/실패 수)를 **실제 출력 그대로**
- 러너를 설치했으면 설치한 패키지와 바뀐 파일
- 소스 버그로 판단한 실패: 파일·라인과 근거
- 테스트를 쓰지 않은 대상과 그 이유 (예: 타입 정의만 있음, 외부 SDK 래퍼라 통합 테스트 대상)

**선호 기록:** `prefs:learn`의 실행 규칙을 따른다. 최상위 작업이면 마칠 때 한 번 실행하고, `git:ship` 같은 다른 스킬에서 호출됐으면 실행하지 않고 신호만 보고에 넘긴다. 이 작업의 신호 예: 케이스를 더 넣거나 빼라고 한 것, 목 처리 방식을 바꾸라고 한 것.

## 하지 않을 것

- 사용자가 요청하거나 동의하지 않은 러너·테스트 라이브러리 설치하기
- 소스 로직 고치기. 테스트 작성에 꼭 필요한 export 추가도 먼저 보고하고 묻는다
- 기존 테스트 설정(전역 setup, 설정 파일)을 동의 없이 바꾸기. 러너를 새로 설치할 때 만드는 설정은 예외다
- 실패한 테스트를 `skip`·`todo`로 바꾸거나 지워서 통과시키기
- 실행하지 않고 "통과"라고 보고하기
- 커밋·푸시하기
