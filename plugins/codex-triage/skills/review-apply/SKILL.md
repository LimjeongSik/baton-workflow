# Codex 리뷰 → 판단 → 반영

작업 단위를 커밋한 직후 codex에게 리뷰를 받고, **타당한 지적만 골라 반영**하는 워크플로우다.
핵심 원칙: **리뷰는 제안일 뿐이고, 판단은 메인(컨트롤러) 에이전트가 한다.** 지적받았다는 이유만으로 고치지 않는다.

subagent-driven development로 진행 중이라면 채택한 수정은 해당 Task의 구현 서브에이전트에게 맡겨도 되고 직접 편집해도 된다. 어느 쪽이든 채택/기각 판단은 메인 에이전트가 한다.

리뷰 범위는 git ref `refs/codex-review/last`(마지막 리뷰 완료 지점)부터 HEAD까지다.
ref가 없으면 첫 커밋부터 리뷰한다. 기존 프로젝트에 처음 도입할 때는 `--base <ref>`로 범위를 좁힌다 (예: `--base main`).

## 0. 사전 확인

```bash
git log --oneline refs/codex-review/last..HEAD   # ref가 없으면 생략
git status --short --untracked-files=all
```

- 리뷰할 커밋이 없고 작업 트리도 깨끗하면 그대로 종료한다.
- 커밋하지 않은 소스 변경이 있으면 먼저 품질 게이트를 통과시킨 뒤 커밋한다. 리뷰는 커밋된 변경분을 기준으로 한다.

### 품질 게이트 결정

리뷰 전에 로컬 검사부터 통과시킨다. 여기서 걸리는 문제는 codex에게 물을 필요가 없다.
검사 명령은 다음 우선순위로 정한다:

1. `CLAUDE.md` / `AGENTS.md`에 명시된 lint·typecheck·test 명령
2. `package.json`의 `scripts` 중 `lint`, `typecheck`/`type-check`, `test`. 패키지 매니저는 lockfile로 판단한다 (`bun.lock*` → bun, `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, 그 외 npm). TypeScript 프로젝트에 typecheck 스크립트가 없으면 `tsc --noEmit`을 쓴다.
3. 다른 생태계의 표준 명령 (`Makefile`의 `lint`/`test`, `pyproject.toml`의 ruff·pytest, `cargo clippy`/`cargo test`, `go vet`/`go test ./...` 등)

검사 명령을 찾지 못하면 그 사실을 보고에 적고 넘어간다. 명령을 지어내지 않는다.

## 1. 리뷰 실행

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/codex-review.sh" $ARGUMENTS
```

- 기본 모드는 `adversarial-review`(설계·가정까지 의심하는 리뷰)이고, 범위는 `refs/codex-review/last..HEAD`, 실행은 동기다. 일반 리뷰는 첫 인자로 `review`를 준다.
- Bash `timeout`은 `600000`으로 준다.
- 리뷰 원문은 stdout과 `<저장소 루트>/.claude/review-logs/<HEAD 단축 sha>.md`에 남는다.
- 특정 관점을 강조하려면 마지막 인자로 포커스 텍스트를 붙인다 (예: `"세션 쿠키 검증 경로"`).
- 변경 규모가 크면(대략 파일 15개 또는 800줄 초과) `run_in_background: true`로 띄우고 진행 상황을 확인한다. 결과는 `/codex:status`, `/codex:result`로 조회한다.
- 스크립트가 종료 코드 127로 끝나면 codex CLI나 플러그인 설치 문제다. 우회 인증을 임의로 시도하지 말고, 사용자에게 `/codex:setup`을 안내한 뒤 멈춘다.
- codex가 JSON 파싱 실패나 실행 실패를 보고하면 findings를 추측으로 지어내지 말고, stderr의 핵심 줄만 전달한 뒤 멈춘다.

출력 형태는 `[severity] 제목 (파일:라인)` + 본문 + `Recommendation`이다.

## 2. 판단: 각 지적을 코드로 검증

findings를 그대로 믿지 않는다. **지적마다 해당 파일·라인을 직접 Read해서 확인한 뒤** 채택/기각을 정한다.

먼저 이 저장소의 규약 문서를 파악한다: 루트와 변경된 폴더의 `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, 그리고 그 문서들이 가리키는 스펙·설계 문서.

**채택** (검증된 경우에만):
- 실제 재현 경로가 있는 버그: null/undefined, 경쟁 상태, 처리되지 않은 실패 경로, 잘못된 상태 전이
- 데이터 손실·보안·권한 문제 (인증·토큰 검증 누락 등)
- 타입 안전성 붕괴 (`any` 우회, 실제로 깨진 제네릭)
- 저장소에 명시된 규약 위반: 위 규약 문서, 폴더·파일 네이밍 컨벤션, 디자인 토큰 사용 규칙 등
- 빈 상태/로딩/에러 처리 누락 중 사용자에게 실제로 보이는 것

**기각** (기각도 정상적인 결론이다):
- 지적한 파일·라인·코드 경로가 실제로 존재하지 않음 (환각)
- 이번 변경 범위 밖의 기존 코드에 대한 지적 → 반영하지 않고 "후속 과제"로만 보고
- 이 프로젝트에 아직 없는 인프라를 전제한 지적 (스펙에 없는 계층·기능)
- 스타일·네이밍 취향, 린터가 이미 강제하는 항목
- 근거 없이 "~할 수도 있다" 수준인 추측, 또는 `confidence`가 낮고 코드로 확인되지 않는 것
- 스펙이나 프로젝트 아키텍처 방향과 충돌하는 제안

**애매하면 반영하지 않는다.** 확신이 서지 않는 지적은 "보류"로 분류하고, 판단 근거와 함께 사용자에게 넘긴다.
`critical`/`high`는 반드시 코드로 검증까지 마친다. 검증 없이 기각하지 않는다.

### 심각도 정책

프로젝트 문서에 별도 정책이 있으면 그것을 따른다. 없으면 아래 기본값을 쓴다.

| 심각도 | 처리 |
|---|---|
| critical / high | 코드로 검증한 뒤 **사용자 확인 없이 바로 수정** → 품질 게이트 → 재리뷰 1회 |
| medium | 현재 Task 범위의 실제 결함이면 수정, 아니면 후속 과제로 보고 |
| low | 보고만 한다 |
| 환각·범위 밖·취향 | 기각 |

## 3. 반영

- 채택한 지적만, **지적한 범위 안에서 최소한으로** 수정한다.
- 리뷰가 언급하지 않은 리팩터링·정리·개선을 끼워 넣지 않는다.
- 이번 변경분 밖의 파일을 건드려야만 고칠 수 있으면, 고치기 전에 먼저 그 사실을 알린다.
- 리뷰의 `Recommendation`이 이 코드베이스에 맞지 않으면 의도(무엇을 막으려는지)만 취하고, 구현은 프로젝트 관례에 맞춘다.
- 반영분은 커밋한다. 커밋 메시지는 저장소 컨벤션을 따르고, 특별한 컨벤션이 없으면 `fix: codex 리뷰 반영 - <요약>`을 쓴다.

## 4. 검증

0단계에서 정한 품질 게이트를 다시 돌려 수정 때문에 새 위반이 생기지 않았는지 확인한다. 실패하면 통과할 때까지 고친다.

## 5. 재리뷰 (조건부)

`critical` 또는 `high`를 실제로 반영한 경우에만 1회 더 돌린다. **최대 2라운드까지만 한다.**
2라운드 뒤에도 새 findings가 남으면 반영하지 말고 보고만 한 뒤 사용자 판단을 받는다. 루프를 돌지 않는다.

## 6. 종료: 기준점 갱신

리뷰와 반영이 끝나면 기준점을 옮긴다. 리뷰가 필요 없는 변경이라고 판단해 건너뛸 때도 옮긴다:

```bash
git update-ref refs/codex-review/last HEAD
```

codex 실행 자체가 실패했다면 기준점을 옮기지 않는다.

이 ref가 생긴 저장소에서는 플러그인의 Stop 게이트가 켜져서, 리뷰되지 않은 커밋이 남은 채로 종료하려 하면 이 스킬을 실행하라고 요구한다. 게이트를 끄려면 `CODEX_TRIAGE_GATE=0`을 설정하거나 `git update-ref -d refs/codex-review/last`로 ref를 지운다.

## 7. 보고

다음 표를 반드시 출력한다:

| 지적 | 심각도 | 판단 | 근거 | 반영 내용 |
|---|---|---|---|---|
| 제목 (파일:라인) | critical/high/medium/low | 반영 / 기각 / 보류 | 코드 확인 결과 한 줄 | 수정 요약 또는 `-` |

표 아래에 다음을 적는다:
- 품질 게이트 결과 (실행한 명령과 결과). 실패했으면 숨기지 말고 그대로 적는다.
- 기각/보류한 지적 중 후속 과제로 남길 것

## 하지 않을 것

- 리뷰 지적을 검증 없이 일괄 반영하기
- 리뷰 결과를 근거로 푸시하기 (사용자가 따로 요청할 때만 한다)
- codex 실행에 실패했을 때 리뷰 결과를 상상해서 채우기
- 리뷰가 조용히 끝났다고 "지적 없음"으로 보고하기. 실행 실패와 findings 0건은 구분해서 보고한다.
