# 테스트 작성 규칙

`feature:tester`와 `test:write`가 함께 따르는 기준이다. 부른 쪽 문서는 이 문서에 없는 것(대상, 실행 범위, 보고 형식)만 정한다.

## 1. 하네스 파악

1. `CLAUDE.md` / `AGENTS.md`에서 테스트 규칙과 함정을 찾는다.
2. 테스트 설정 파일(`jest.config.*`, `vitest.config.*`, `pytest.ini`/`pyproject.toml`, `jest.setup.*`, `setupTests.*`, `conftest.py` 등)을 읽는다.
   - 위치·이름 규칙(`testMatch`, `include`): 이 밖에 둔 테스트는 실행되지 않는다
   - 전역 setup에서 이미 목킹한 모듈: 다시 목킹하면 깨질 수 있다
   - 경로 별칭이 테스트에서도 동작하는지
3. 기존 테스트 2~3개를 읽고 import·렌더·쿼리·비동기 처리·목킹·픽스처 패턴을 그대로 따른다. 라이브러리 API는 기억이 아니라 설치된 버전과 기존 테스트를 기준으로 한다.
4. 실행 명령은 프로젝트 스크립트(`package.json`의 `test` 등)를 거친다. 런타임 내장 러너를 직접 부르지 않는다. `bun test`는 Bun 내장 러너라 jest preset·setup을 건너뛰고, `bun run test`는 프로젝트 스크립트를 실행한다.

러너가 아예 없으면 설치 여부는 부른 쪽 문서를 따른다.

## 2. 위치

위에서부터 처음 해당하는 것을 따른다.

1. **프로젝트가 명시한 규칙:** 루트·폴더 `CLAUDE.md`, `AGENTS.md`, 러너 설정의 위치 규칙
2. **기존 배치:** 대상 파일의 테스트가 이미 있으면 그 파일에 추가한다. 없으면 저장소에서 가장 많이 쓰는 배치(`__tests__/`, 같은 폴더의 `.test` 파일, 최상위 `tests/`)를 따른다
3. **언어별 기본값:** JS/TS는 같은 폴더의 `__tests__/<이름>.test.ts(x)`, Python은 `tests/test_<모듈>.py`, Go는 같은 폴더의 `<이름>_test.go`, Rust는 같은 파일의 `#[cfg(test)]` 모듈

기존 테스트를 다른 위치로 옮기지 않는다.

## 3. 기대값의 출처

- **요구사항과 공개 계약에서 기대값을 정한다.** 요구사항은 부른 쪽이 준 완료 조건과 사용자 요청이고, 공개 계약은 export된 시그니처·타입·props·문서·API 응답 형식이다.
- 소스는 호출 방법(export 이름, 인자, 렌더 방법)을 알기 위해 읽는다. 구현 코드에서 기대값을 역산하지 않는다.
- 구현이 요구사항과 다르게 동작하면 테스트를 구현에 맞추지 않는다. 실패하는 테스트로 두고 "요구사항과 다름"으로 보고한다.
- 요구사항이 없으면 공개된 동작을 목록으로 만들어 기준으로 삼는다. 현재 동작이 의도인지 판단할 수 없는 것은 보고에 적는다.

## 4. 무엇을 테스트하나

구현 세부가 아니라 동작을 테스트한다.

- **순수 로직**(포맷터, 검증, 상태 전이, 계산): 정상값, 경계값, 잘못된 입력
- **컴포넌트**: 렌더 결과와 사용자 상호작용의 결과. 접근성 쿼리(`getByRole`, `getByLabelText`)를 우선한다
- **핸들러·API**: 성공, 실패, 빈 결과, 권한 없음 같은 주요 분기와 부수효과 호출
- **흐름**: 실제 사용자가 밟는 경로대로 통합 테스트
- **외부 경계**(네트워크, 시간, 난수, 파일): 그 경계만 목킹한다. 테스트 대상 자체를 목킹하지 않는다

하지 않는다:

- 스냅샷 테스트. 깨지면 무비판적으로 갱신하게 되어 회귀를 못 잡는다
- 테스트끼리 상태 공유. 스토어, 데이터 패칭 클라이언트, 타이머, 목은 테스트마다 새로 만들거나 되돌린다
- 커버리지 숫자를 채우려는 의미 없는 테스트 (getter 호출, 상수 비교 등)

## 5. 실행

1. 쓰거나 고친 테스트 파일부터 실행한다. 예: `<runScript> test -- src/lib/__tests__/format.test.ts`
2. 그다음 실행 범위(관련 테스트까지인지 전체인지)는 부른 쪽 문서를 따른다.
3. 타입 검사가 있는 프로젝트면 테스트 파일에 타입 오류가 없는지 확인한다. 테스트 파일의 타입 오류도 실패다.

출력을 줄여 보더라도 성공 여부는 종료 코드로 판단한다.

## 6. 실패했을 때

먼저 테스트가 틀렸는지 소스가 틀렸는지 가린다.

- **테스트가 틀렸으면**(잘못된 셀렉터, 비동기 대기 누락, 잘못된 목) 테스트를 고친다. 단언을 약하게 바꿔서 통과시키지 않는다.
- **소스가 틀렸으면** 소스를 고치지 않는다. 어느 파일 어느 줄이 어떤 입력에서 무엇을 잘못 내는지 근거와 함께 보고하고 멈춘다. 실패하는 테스트는 그대로 둔다. 그 테스트가 버그를 증명한다.
- 테스트를 두 번 고쳤는데도 원인을 가리지 못하면 멈추고 보고한다.
- 실패한 테스트를 `skip`·`todo`로 바꾸거나 지우지 않는다. 하네스 설정(설정 파일, 전역 setup)을 바꿔야만 테스트할 수 있으면 바꾸지 말고 이유와 함께 보고한다.
- 실행하지 않은 테스트를 "통과"로 보고하지 않는다.
