# 기능 개발: 계획 → 구현 → 테스트 → 검증

구현과 테스트를 **다른 에이전트가** 맡는다. 같은 에이전트가 코드와 테스트를 함께 쓰면, 자기 구현에 맞춘 테스트가 나와서 버그를 못 잡는다. 테스트의 기대값은 구현 보고가 아니라 **요구사항(완료 조건)**에서 온다.
서브에이전트는 **작업 규모만큼만** 띄운다. 에이전트마다 저장소를 처음부터 다시 읽으므로, 작은 작업에 여럿을 띄우면 컨텍스트가 중복되고 비용만 는다.
**메인은 지휘와 판단을 맡는다.** 각 에이전트의 보고를 그대로 믿지 않고, 마지막 검증은 메인이 직접 돌린다.

요청: `$ARGUMENTS`

## 0. 파악과 기준선

```bash
git status --short --untracked-files=all
```

- 작업 트리에 관련 없는 변경이 섞여 있으면, 이어서 진행해도 되는지 사용자에게 묻는다.
- 루트 `CLAUDE.md` / `AGENTS.md`와 진행·결정 문서(`docs/PROGRESS.md`, ADR 등)를 읽는다.
- 이 프로젝트의 작업 방식 프로필(prefs 플러그인이 프로젝트 루트 `learn/learned.md`에 학습해 두고 세션 시작 시 넣는다)이 컨텍스트에 있으면 작업 방식·선호 기술·코드 패턴·피하는 것 절을 따른다. `[확정]` 항목은 묻지 않고 기본값으로 따르고, `[추정]` 항목은 다른 근거가 없을 때만 따르고 따랐으면 보고에 밝힌다. 이번 요청과 다르면 요청을 따른다.
- **검사 명령을 정한다:** `CLAUDE.md`에 적힌 명령 → `package.json` 스크립트(lockfile로 패키지 매니저 판단) → 표준 도구 순서로 찾는다. 명령을 지어내지 않는다.
- 기준선으로 lint → 타입 검사 → 테스트를 돌리고 **스위트·케이스 수를 적어 둔다.** 기준선이 이미 실패하면 그 사실을 먼저 알린다.

## 1. 계획

- 요구사항이 모호해서 결과가 크게 달라지는 지점(데이터 출처, 화면 흐름, 권한 등)이 있으면 **구현 전에** 사용자에게 묻는다. 관례로 정할 수 있는 것은 묻지 않는다.
- **완료 조건을 먼저 쓴다.** 사용자 관점의 동작으로, 확인할 수 있게 쓴다 (예: "목록이 비면 '항목 없음'과 추가 버튼을 보인다", "저장 실패 시 입력값을 유지하고 에러를 보인다"). 정상·실패·빈 상태·경계 조건을 빠뜨리지 않는다. 이 목록이 테스트의 기준이 되고, 구현 에이전트와 테스트 에이전트에게 **같은 원문**으로 넘어간다.
- 기능을 구현 단위로 나누고, **단위마다 건드릴 파일**을 적는다.
- 파일이 겹치지 않는 단위끼리만 병렬로 진행할 수 있다. 겹치면 순차로 진행한다.
- 새 의존성, 라우팅 구조 변경, 전역 상태 방식 변경, 스키마·API 계약 변경이 필요하면 계획 단계에서 사용자 승인을 받는다.

### 규모에 맞춘 에이전트 배치

| 규모 | 기준 (대략) | 구현 | 테스트 |
|---|---|---|---|
| 작음 | 단위 1개, 파일 3개 이하, 새 화면·새 의존성 없음 | 메인이 직접 | `feature:tester` 1개 (완료 조건만 넘긴다) |
| 보통 | 단위 1~2개, 또는 새 화면 1개 | `feature:implementer` 1개 | `feature:tester` 1개 |
| 큼 | 파일이 겹치지 않는 단위 여러 개 | 단위마다 `feature:implementer` (한 메시지에서 병렬) | 단위를 묶어 `feature:tester` 1~2개 |

- 작음이어도 **테스트는 다른 에이전트가 쓴다.** 구현한 쪽이 테스트까지 쓰지 않는다는 원칙은 규모와 상관없다.
- 한 줄 수정·오타·설정 값 변경처럼 동작이 바뀌지 않으면 테스트 에이전트도 띄우지 않고, 기존 테스트만 실행한다. 보고에 그 판단을 적는다.
- 서브에이전트에게는 파일 전문을 붙이지 않고 **경로와 범위**를 넘긴다. 에이전트가 직접 읽는다. 0단계에서 정한 검사 명령, 결정 사항, 선호 프로필 항목처럼 에이전트가 스스로 찾기 어려운 것만 요약해 넘긴다.

## 1.5 디자인 (새 화면이나 시각적 변경이 있을 때)

구현 에이전트를 띄우기 **전에** 메인이 디자인을 확정한다. 서브에이전트는 사용자에게 승인을 물을 수 없기 때문이다.

- `ui:design` 스킬을 쓸 수 있으면 메인이 직접 실행한다. **목업 이미지를 만들고 사용자 승인을 받는 단계(5단계)까지만** 진행하고, 승인된 목업 경로를 기록한다.
- 프로젝트에 디자인 시스템이 있고 기존 패턴을 그대로 쓰는 작은 변경이면(기존 폼에 필드 하나 추가 등) 건너뛴다.
- `ui` 플러그인이 없으면 이 단계를 건너뛰고, implementer가 `frontend-design`으로 계획을 세우게 한다.

## 2. 구현: `feature:implementer`

- 1단계에서 "작음"이면 이 단계는 메인이 직접 하고, 아래 implementer 규칙(관례 따르기, 테스트 파일 쓰지 않기, 마칠 때 검사)을 그대로 지킨다.
- 프롬프트에 넣을 것: 구현 단위의 **목표와 완료 조건(1단계 원문)**, 건드릴 파일 범위, 0단계에서 정한 **검사 명령**, 사용자가 정한 결정 사항, **선호 프로필의 해당 항목**(선호 기술·코드 패턴·피하는 것. 서브에이전트가 프로필을 받는다고 가정하지 않는다), 그리고 UI 작업이면 **승인된 목업 경로(HTML·PNG)와 디자인 계획 요약**.
- 파일이 겹치지 않는 단위는 한 메시지에서 병렬로 띄운다.
- 에이전트가 "판단이 막힘"으로 멈추면, 메인이 결정할 수 있는 것은 결정해서 다시 넘기고, 아키텍처 결정이면 사용자에게 묻는다.

## 3. 테스트: `feature:tester`

- **1단계의 완료 조건 원문**, 사용자의 원래 요청, 변경된 파일 경로, 테스트 실행 명령, 선호 프로필의 코드 패턴 절에서 테스트 관련 항목을 넘긴다. 구현 보고의 "테스트가 필요한 동작 목록"은 **보충 자료**로만 넘기고, 구현 에이전트의 설명(왜 그렇게 짰는지)은 넘기지 않는다. 테스트 에이전트가 구현의 가정을 물려받지 않게 하기 위해서다.
- 테스트가 완료 조건 중 무엇을 덮었고 무엇을 못 덮었는지 보고받는다. 못 덮은 조건이 있으면 이유를 확인한다.
- 테스트 에이전트가 **소스 버그를 보고하면:** 메인이 해당 파일·라인을 직접 확인한다. 실제 버그면 그 보고를 근거로 `implementer`에게 수정을 맡기고, 다시 테스트한다. **이 왕복은 최대 2회까지만 한다.** 그래도 남으면 멈추고 사용자에게 보고한다.
- 테스트 러너가 없다고 보고되면, `test:write` 스킬이 있을 때 그 스킬로 설치 여부를 사용자에게 묻는다. 설치하면 테스트 에이전트를 다시 띄운다. 스킬이 없거나 사용자가 거절하면 테스트 단계를 건너뛰고 보고에 적는다.

## 4. 검증: 메인이 직접 돌린다

```bash
<lint> && <typecheck> && <test> 2>&1 | tail -20
git diff --stat
```

- 기준선 대비 테스트 수가 **늘었는지** 확인한다. 기존 테스트가 줄었거나 기존 단언이 바뀌었으면 원인을 찾는다.
- `git diff`를 읽고 요청 범위 밖의 변경이 섞였는지 본다. 섞였으면 되돌린다.
- UI를 바꿨으면, 사람이 눈으로 봐야 할 화면과 조작 순서를 정리해 둔다.

## 5. 보안 점검 (해당할 때만)

인증·토큰·권한·외부 입력 처리·네트워크·앱 권한·의존성을 건드렸고 `security:auditor` 에이전트를 쓸 수 있으면 감사를 맡긴다.
감사는 지적만 한다. 각 지적은 메인이 코드로 검증해서 타당한 것만 `implementer`에게 수정을 맡긴다. `critical`/`high`를 기각하려면 왜 악용될 수 없는지 코드로 보여야 한다.

## 6. 보고

- 무엇을 만들었는가 (사용자 관점 한두 줄)
- 추가/수정 파일과 핵심 결정
- 검사 결과: 실행한 명령과 기준선 대비 숫자 (`42 suites / 310 tests → 45 / 338`)
- 보안 점검 결과 (했으면)
- 사람이 확인해야 할 화면·조작, 남은 후속 과제

프로젝트에 진행 문서(`docs/PROGRESS.md` 등)가 있으면 이번 작업을 반영한다. `progress:update` 스킬을 쓸 수 있으면 그 스킬로 갱신한다.

새 도메인 폴더를 만들었거나 폴더의 계약·규칙을 바꿨고 `context:sync` 스킬을 쓸 수 있으면, 그 폴더 경로를 인자로 실행해 하위 CLAUDE.md와 루트 목록을 맞춘다.

**선호 기록:** 이번 작업에서 사용자가 결과를 고치게 했거나, 선택지 중 하나를 골랐거나, 제안을 거절했거나, "앞으로는" 같은 지시를 했거나, 사용자의 행동에서 방식이 드러났다고 판단했고(예: Claude가 만든 결과를 사용자가 직접 같은 방향으로 고침) `prefs:learn` 스킬을 쓸 수 있으면, 그 내용(예: 계획 단계에서 고른 방식, 1.5단계에서 고른 목업 방향과 수정 요청, 구현 뒤 고치라고 한 부분)를 요약해 넘겨 실행한다. 이번 작업에만 해당하는 내용은 넘기지 않는다.

**커밋·푸시는 하지 않는다.** 사용자가 요청하면 `git:ship` 스킬로 진행한다. 그 스킬이 감사와 리뷰까지 거친다.

## 하지 않을 것

- 구현한 쪽(구현 에이전트, 또는 작은 작업에서 직접 구현한 메인)이 테스트를 쓰거나, 테스트 에이전트에게 소스를 고치게 하기
- 작은 작업에 에이전트를 여러 개 띄우기, 에이전트 프롬프트에 파일 전문 붙이기
- 에이전트 보고만 믿고 검증 생략하기
- 테스트를 약화시켜서 통과시키기
- 요청 범위 밖의 리팩터링·개선을 끼워 넣기
