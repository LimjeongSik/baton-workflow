# ui

[frontend-design](https://github.com/anthropics/claude-plugins-official) 스킬을 기반으로, 레퍼런스를 반영하고 분야에 맞춰 최적화한 UI/UX를 디자인합니다. **코드보다 목업 이미지가 먼저**입니다. 리서치 에이전트가 실제 제품·최근 트렌드·컬러 레퍼런스를 찾아 정리한 근거로 목업을 만들고, 시니어 UI/UX 리뷰 에이전트가 리뷰하고 고친 목업을 사용자가 승인하면 그것을 구현합니다.

## 0.2.3에서 바뀐 점

- **규칙은 한 곳에만:** 본문은 단계 순서, 에이전트에 넘길 것, 결과 확인, 승인, 예외 처리만 남기고 컬러·타이포·카피의 상세 규칙은 `references/`에만 둡니다. 리뷰어의 카피 항목은 `korean-copy.md`의 검수 순서를 따르라는 한 줄로 줄였고, AI 티 점검표의 카피 절은 번역투·말투·표기 항목을 `korean-copy.md`에 맡기고 과장·상투어·반복 리듬과 가짜 콘텐츠만 남겼습니다
- **짧은 최종 보고:** 디자인 근거는 `.design/` 문서에 두고, 최종 보고는 무엇이 달라졌는지, 검증 결과, 사용자가 확인할 것, 문서 경로만 적습니다
- **선호 기록 한 번:** `feature:build` 안에서 실행되면 선호 학습을 직접 하지 않고 신호만 넘깁니다

## 0.2.2에서 바뀐 점

- **타이포그래피 규칙 재작성:** 예전 규칙이 권하던 "아주 굵은 제목 + 크게 줄인 자간(`-0.03em`) + 좁은 행간"이 생성형 한국어 화면의 기본값이라, 한글 기준으로 다시 잡았습니다. 큰 제목은 600~700 굵기, 자간 `0`~`-0.02em`, 여러 줄이면 행간 `1.3`~`1.4`에서 출발하고, 값마다 이유를 적습니다. 서체 후보와 고르는 기준, 한 줄 길이(30~45자), `text-wrap: balance`·`pretty`로 마지막 줄 한 단어 막기를 넣었습니다
- **한국어 카피 문서 분리(`references/korean-copy.md`):** 번역투뿐 아니라 추상적 비유·피동 남발·불분명한 수식 관계·지나친 압축·어려운 한자어·흐름(문장 연결, 제목과 본문의 역할, 섹션 순서)·AI가 쓴 티가 나는 리듬과 상투어를 예문과 함께 다룹니다. 다듬으면서 기능·주체·조건·시점·확실성을 바꾸지 않는 의미 보존을 첫 원칙으로 두고, 랜딩(가치와 설득의 흐름)과 제품 화면(위치·상태·다음 행동)의 기준을 나눴습니다. 상태와 행동 결과 구분, 원인을 단정하지 않는 오류 문구, 안전할 때만 쓰는 재시도 안내, 종류별 빈 상태도 다룹니다. 예문에도 확인되지 않은 기능이나 약속을 넣지 않습니다. 항목은 금지 목록이 아니라 "오해를 만드는가"로 판단합니다. 검수는 화면 종류 정하기 → 흐름 읽기 → 소리 내어 읽기 → 문장마다 질문 → 원래 문장과 대조 순서로 리서치·리뷰·구현에서 거치고, 고친 문장은 전후로 남깁니다

- **렌더링 대기 상한:** 웹폰트·이미지는 최대 8초까지만 기다리고, 끝나지 않은 것과 로딩에 실패한 이미지는 출력 셋째 줄부터 경고로 보여 줍니다. 느린 이미지 하나 때문에 페이지 로딩에서 멈추지 않고, 화면 밖 지연 로딩 이미지도 전체 페이지 캡처에 찍힙니다
- **재촬영 기준:** Chrome 대체 경로("뷰포트만")에서는 표시가 아니라 PNG에서 내용이 잘렸는지로 판단하고, 잘렸을 때만 한 번 더 찍습니다. 헤드리스 Chrome은 500px보다 좁은 폭을 500px로 배치해 오른쪽이 잘린 그림을 내므로, 모바일 폭에서는 Chrome 대체 경로를 쓰지 않고 실패로 알립니다(Playwright 필요)
- **기존 시스템의 대비 실패:** 토큰을 임의로 바꾸지도 멈추지도 않습니다. 시스템 색 그대로 목업을 내고, 실패한 조합과 최소 수정안을 보여 줍니다. 공용 토큰은 다른 화면에도 영향을 주므로 사용처를 먼저 확인하고, 기존 토큰 재조합 → 컴포넌트 의미 토큰 → 공용 토큰 변경 순으로 검토한 해결책 중에서 사용자가 고르게 합니다
- **팔레트 검사 종료 코드:** 0 통과, 1 대비 실패, 2 입력 오류(잘못된 hex·알 수 없는 옵션·빠진 값)로 나눕니다. 입력 오류가 있으면 아무것도 검사하지 않습니다. 대비 실패마다 명도만 조정한 최소 수정안을 함께 냅니다

## 0.2.1에서 바뀐 점

- **판단 우선순위 통일:** 본문과 두 에이전트가 `references/priorities.md` 하나를 따릅니다. 기존 디자인 시스템이 있으면 그것이 기본이고, 레퍼런스·리서치는 시스템과 충돌하지 않는 축(레이아웃·밀도·위계·카피 톤)에만 반영합니다. 시스템은 사용자가 명시적으로 요청할 때만 바꿉니다
- **리서치 근거 구분:** 소스마다 확인 방식(텍스트 / 이미지 / 실제 화면)을 적고, 레이아웃·타이포·면적 비율 같은 시각적 관찰은 이미지나 실제 화면으로 본 소스에서만 가져옵니다
- **상태 목록:** 계획에 상태 × 화면 폭 표를 두고 상태마다 목업에서 확인 / 구현에서 확인 / 해당 없음을 정합니다. 리뷰와 구현 검증이 같은 목록을 기준으로 합니다
- **리뷰 범위 분리:** 리뷰를 시각 확인 완료와 구현 후 검증 필요(키보드, 포커스 복귀, 스크린리더, 실제 과업 경로)로 나눕니다. 구현 뒤에는 핵심 과업 하나를 실제로 해 봅니다
- **AI 티 점검표:** 겉모습을 단정하는 대신 "이유 없이 반복했거나 위계·사용성을 해치는가"를 묻습니다. 분야 관례와 디자인 시스템에서 나온 선택은 걸리지 않습니다
- **렌더링 신뢰도:** 웹폰트·이미지 로딩을 기다려 전체 페이지를 찍고, 캡처 범위(전체 페이지 / 뷰포트만)를 출력합니다. 임시 파일에 찍어 성공했을 때만 교체하므로 예전 PNG가 남아 있어도 성공으로 오판하지 않고, 실패하면 시도별 오류를 보여 줍니다
- **팔레트 검사:** 버튼 글자/버튼 배경처럼 실제로 겹쳐 쓰는 조합을 `--text`·`--large`·`--ui`로 받아 검사합니다. 스타일 경고와 대비 실패를 나누고, 대비 실패가 있으면 종료 코드 1입니다
- **승인 기록과 작업 규모:** 승인하면 `.design/approved/<화면>.md`에 버전·방향·화면 폭·상태·남은 문제를 남깁니다. 컴포넌트 추가 같은 작은 작업은 기존 리서치를 재사용하고 조사 범위를 줄입니다

## 0.2.0에서 바뀐 점

- `ui:reviewer`가 목업을 심각도별로 리뷰하고(`.design/reviews/`), 고친 다음 버전을 만든 뒤에 사용자 승인을 받습니다

## 사용법

```
/ui:design 정비 기사용 작업 지시 대시보드 [레퍼런스 이미지 경로나 URL]
```

"이 레퍼런스처럼 랜딩 페이지 디자인해줘"처럼 자연어로 요청해도 됩니다.

## 흐름

1. frontend-design 스킬 호출 (필수)
2. 분야 판별(대시보드 / 모바일 앱 / 웹 앱 / 랜딩 / 커머스 / 콘텐츠), 기존 디자인 시스템 확인, 작업 규모(전체 / 가벼움) 결정
3. **리서치와 첫 목업 (`ui:researcher`):** 같은 분야에서 실제로 운영 중인 제품, 최근 12개월의 UI/UX 트렌드, 컬러 레퍼런스를 웹에서 찾아 직접 열어 보거나 캡처해서 `.design/research/<화면>.md`에 정리합니다. 트렌드는 AI 티 점검표로 걸러 쓸지 말지 판정합니다. 이 정리를 근거로 디자인 계획과 상태 × 화면 폭 목록을 세우고, 팔레트 검사와 AI 티 점검을 거쳐 목업 v1을 만듭니다
4. **시니어 리뷰와 개선 (`ui:reviewer`):** 목업 PNG를 보고 과업·위계·리듬·타이포·컬러·상태·접근성·카피를 리뷰해 심각도별로 지적하고(`.design/reviews/`), 지적을 반영한 v2를 만들어 v1과 비교해 확인합니다. PNG로 판단할 수 없는 키보드·포커스·스크린리더·과업 경로는 구현 후 검증 목록으로 넘깁니다
5. **사용자 승인** (이대로 / 수정 후 다시 / 다른 방향). v1과 v2를 함께 보여주고, 승인하면 `.design/approved/<화면>.md`에 기록합니다
6. 승인된 목업 기준으로 구현 → 스크린샷 비교와 핵심 과업 실제 수행 → 보고

판단이 부딪히면 `references/priorities.md`를 따릅니다. 기존 디자인 시스템이 있으면 그것이 기본이고, 레퍼런스와 리서치는 레이아웃·밀도·위계처럼 시스템과 충돌하지 않는 부분에 반영합니다. 새로 시스템을 잡을 때는 사용자가 준 레퍼런스가 리서치보다 앞섭니다. 서브에이전트 안에서 실행돼 에이전트를 띄울 수 없으면 두 역할을 순서대로 직접 합니다.

## 컬러 정책

새 디자인 시스템을 잡을 때는 밝은 면을 기본으로 합니다. 근거 없는 다크·네이비·인디고·보라 그라데이션, Tailwind 기본 팔레트, 크림·테라코타는 피합니다. 기존 디자인 시스템이 있으면 그것을 따르고, 새로 잡을 때는 사용자가 준 레퍼런스가 정한 방향을 따릅니다.

## 타이포와 한국어 카피

서체는 주제에서 이유를 찾아 고르고, 모든 텍스트 스타일에 자간·행간을 직접 정해 값마다 이유를 적습니다. 한글은 자간을 많이 줄이지 않고(큰 제목 `0`~`-0.02em`), 큰 제목은 600~700 굵기와 행간 `1.3`~`1.4`에서 출발해 목업에서 눈으로 보고 조정합니다. "아주 굵은 제목 + 크게 줄인 자간 + 좁은 행간"은 생성형 화면의 기본값이라 피합니다.

화면의 한국어는 `references/korean-copy.md`를 따릅니다. 실제 사용자가 하는 말로, 처음 보는 사람이 한 번에 이해하게, 그리고 사실과 맞게 씁니다. 자연스럽게 고치면서 기능·주체·조건·시점·확실성을 바꾸지 않습니다. 랜딩은 가치와 설득의 흐름을, 제품 화면은 지금 위치·상태·다음 행동이 분명한지를 봅니다. 번역투·추상적 비유·불필요한 피동·불분명한 수식 관계·지나친 압축·반복 리듬은 오해를 만들거나 읽기를 막을 때 고칩니다.

## 목업 렌더링

Playwright(프로젝트 설치본 → 최신 버전) → 로컬 Chrome 계열 브라우저 순으로 찾습니다. 같은 스크립트로 레퍼런스 사이트 URL도 캡처합니다. 처음 실행할 때 Playwright 헤드리스 브라우저를 내려받을 수 있습니다.

만든 이미지와 문서는 모두 프로젝트 루트의 `.design/` 폴더에 저장됩니다. 리서치 문서와 레퍼런스 캡처는 `.design/research/`, 리뷰는 `.design/reviews/`, 목업은 `.design/mockups/`, 승인 기록은 `.design/approved/`, 구현 후 스크린샷은 `.design/screenshots/`에 들어가며, 승인을 받을 때와 보고할 때 이 폴더를 열어 확인하라고 안내합니다. 커밋하지 않으려면 `.design/`을 `.gitignore`에 추가하세요.
