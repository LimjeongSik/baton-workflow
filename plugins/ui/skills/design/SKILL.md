# UI 디자인

**가장 중요한 것은 디자인이다.** 동작하는 화면은 최소 조건일 뿐이다. 결과물은 "이 제품을 위해 사람이 내린 선택"으로 보여야 하고, 어느 프로젝트에나 나올 법한 기본값으로 보이면 실패다.

요청: `$ARGUMENTS`

## 0. frontend-design을 먼저 불러온다 (필수)

**가장 먼저 `frontend-design:frontend-design` 스킬을 호출한다.** 그 스킬의 원칙(주제에서 출발하기, 타이포그래피, AI 기본값 목록, 계획 → 검토 → 구현 → 자기비평 흐름, 카피 작성 원칙)이 이 스킬의 바탕이다. 이 스킬은 그 위에 레퍼런스, 분야, 컬러 정책, 자간·행간, 한국어 카피 기준을 더한다.

**지침끼리 부딪히면 `${CLAUDE_SKILL_DIR}/references/priorities.md`를 따른다.** 요약하면: 사용자의 명시적 요청이 가장 앞선다. 기존 디자인 시스템이 있으면 그것이 기본이고, 레퍼런스·리서치·선호 프로필은 시스템과 충돌하지 않는 축(레이아웃·밀도·위계·카피 톤)에만 반영한다. 시스템을 바꾸는 것은 사용자가 명시적으로 요청했을 때만 한다. 새로 시스템을 잡을 때는 사용자 레퍼런스 → 프로필 `[확정]` → 리서치 → 이 스킬 → 프로필 `[추정]` → frontend-design 순이다. 두 서브에이전트도 같은 문서를 따른다.

스킬을 찾을 수 없으면 디자인을 시작하지 않는다. 사용자에게 `/plugin install frontend-design@claude-plugins-official` 설치를 안내하고 멈춘다.

## 1. 맥락 파악

- **사용자 선호를 읽는다:** 이 프로젝트의 작업 방식 프로필(prefs 플러그인이 프로젝트 루트 `learn/learned.md`에 학습해 두고 세션 시작 시 넣는다)이 컨텍스트에 있으면 작업 방식·디자인 스타일·글쓰기·피하는 것 절을 따른다. `[확정]` 항목은 묻지 않고 기본값으로 따르고, `[추정]` 항목은 다른 근거가 없을 때만 따르고 따랐으면 보고에 밝힌다. 이번 요청과 다르면 요청을 따른다. 프로필과 기존 디자인 시스템, 이 스킬의 컬러 정책 사이의 우선순위는 `priorities.md`를 따른다.
- **분야를 정한다:** 대시보드·관리 도구 / 모바일 앱 / 웹 앱(SaaS 제품 화면) / 마케팅·랜딩 웹 / 커머스 / 콘텐츠·문서 중 무엇인가. 섞여 있으면 화면 단위로 정한다. 그다음 `${CLAUDE_SKILL_DIR}/references/domains.md`에서 해당 분야 절을 읽는다.
- **주제·사용자·핵심 과업을 한 줄씩 정한다.** 요청에 없으면 제안하고 확인받는다 (frontend-design 원칙).
- **기존 디자인 시스템을 확인한다:** 테마·토큰 파일(`theme/`, `tokens`, `tailwind.config.*`, CSS 변수), 컴포넌트 라이브러리, `CLAUDE.md`의 디자인 규칙.
  - **기존 시스템이 있으면 그 안에서 디자인한다.** 팔레트·타입 스케일을 새로 발명하지 않는다. 이 스킬의 차별화는 레이아웃·위계·밀도·카피·한 곳의 강조로 낸다. 레퍼런스가 시스템과 다른 스타일이어도 시스템을 따르고, 차이는 제안으로만 적는다 (`priorities.md` 2절).
  - 기존 시스템이 없거나 사용자가 새로 잡아 달라고 하면, 컬러 정책으로 새로 만든다 (`priorities.md` 3절).
- **작업 규모를 정한다.** 단계 순서는 바꾸지 않고, 각 단계의 작업량만 조절한다.

  | 규모 | 예 | 리서치 | 목업·리뷰 |
  |---|---|---|---|
  | 전체 | 새 화면, 화면 리디자인, 새 디자인 시스템 | 실제 제품 3~5개, 최근 트렌드, 컬러 레퍼런스 | 화면 전체, 상태 목록 전체 |
  | 가벼움 | 기존 화면에 컴포넌트·섹션 추가, 기존 컴포넌트 수정 | `.design/research/`에 같은 화면이나 같은 분야 리서치가 있으면 재사용하고, 이번 컴포넌트 패턴만 제품 1~2개로 보강한다. 없으면 제품 1~2개만 본다. 트렌드·컬러 조사는 하지 않는다 | 바뀌는 부분과 그 주변만, 그 부분에 해당하는 상태만 |

  색 하나, 문구 하나, 간격 조정처럼 디자인 판단이 거의 없는 수정은 이 스킬을 쓰지 않고 바로 고쳐도 된다. 애매하면 "가벼움"으로 한다.
- **기술 스택을 확인한다:** 프레임워크, 스타일 방식(CSS Modules, Tailwind, styled, RN StyleSheet 등), 아이콘·폰트 로딩 방식. 결과물은 이 스택의 관례대로 쓴다.

## 2. 흐름: 리서치 → 목업 → 시니어 리뷰 → 사용자 승인

목업은 메인이 직접 만들지 않는다. 역할을 나눈다:

| 단계 | 누가 | 결과물 |
|---|---|---|
| 3. 리서치·목업 | `ui:researcher` | `.design/research/<화면>.md`(소스·관찰·트렌드 판정·디자인 계획·상태 목록), 레퍼런스 캡처, `<화면>-v1` HTML·PNG |
| 4. 리뷰·개선 | `ui:reviewer` (시니어 UI/UX) | `.design/reviews/<화면>-v1.md`(시각 확인 완료 / 구현 후 검증 필요), `<화면>-v2` HTML·PNG |
| 5. 승인 | 메인 → 사용자 | `.design/approved/<화면>.md` |
| 6~8. 구현·자기비평·보고 | 메인 | 코드, `.design/screenshots/` |

서브에이전트에게 넘길 것: 요청 원문, 작업 규모(전체/가벼움)와 재사용할 기존 리서치 경로, 분야, 주제·사용자·핵심 과업, 기존 디자인 시스템 요약과 토큰 파일 경로, 사용자가 준 레퍼런스(이미지 경로·URL), 선호 프로필의 디자인 관련 항목(서브에이전트가 프로필을 받는다고 가정하지 않는다), 이 스킬 디렉터리의 절대 경로(`${CLAUDE_SKILL_DIR}`를 풀어서), 저장소 루트와 화면 이름. 파일 전문은 붙이지 않고 경로를 넘긴다.

**`Agent` 도구를 쓸 수 없으면** (이 스킬이 서브에이전트 안에서 실행된 경우 등), 이 플러그인의 `agents/researcher.md`와 `agents/reviewer.md`(`${CLAUDE_SKILL_DIR}/../../agents/`)를 읽고 두 역할을 순서대로 직접 한다. 리뷰는 목업을 만든 관점을 내려놓고, 리뷰어 문서의 축과 심각도 기준으로 PNG를 다시 본다.

`.design/`이 `.gitignore`에 없으면 3단계를 시작하기 전에 추가할지 사용자에게 묻는다.

## 3. 리서치와 첫 목업: `ui:researcher`

`ui:researcher`를 띄운다. 이 에이전트가 하는 일:

- 같은 분야의 실제 운영 제품, 최근 12개월 안의 UI/UX 트렌드, 컬러 레퍼런스를 `WebSearch`로 찾고 **직접 열어 보거나 캡처해서** 취합한다. 조사 범위는 1단계에서 정한 작업 규모를 따른다. 트렌드는 AI 티 점검표로 걸러 채택·변형·쓰지 않음으로 판정한다.
- 소스마다 확인 방식(텍스트 / 이미지 / 실제 화면)을 적는다. 레이아웃·밀도·타이포·면적 비율 같은 시각적 관찰은 이미지나 실제 화면으로 확인한 소스에서만 가져온다.
- 사용자 레퍼런스, 기존 디자인 시스템, 리서치의 우선순위는 `priorities.md`를 따른다.
- 취합을 근거로 디자인 계획을 세운다. 계획에는 **상태 × 화면 폭 목록**이 들어간다. 상태마다 "목업에서 확인 / 구현에서 확인 / 해당 없음"을 정하고, 리뷰와 구현 검증은 이 목록을 기준으로 한다.
- 팔레트 검사(실제 쓰는 글자·배경 조합까지)와 AI 티 점검을 거쳐, 목업 v1을 HTML과 PNG로 만든다.

레퍼런스가 없고 방향이 열려 있으면 서로 확실히 다른 방향 2개(`-a`, `-b`)를 요청해도 된다.

결과를 받으면 메인이 **리서치 문서의 소스 표와 v1 PNG를 직접 확인한다.** 소스가 규모에 비해 적거나, 열어 보지 않은 소스를 인용했거나, 텍스트로만 확인한 소스에서 시각적 관찰을 가져왔으면 보고에 그 사실을 적는다. 렌더링 출력의 둘째 줄이 "뷰포트 … 만"이면 아래쪽이 잘렸는지 PNG에서 확인하고, 셋째 줄부터 "경고:"가 있으면 폰트·이미지가 의도대로 찍혔는지 확인한다. 목업이 렌더링되지 않았으면 4단계로 넘기지 않고 원인을 해결한다.

### 컬러·타이포그래피·카피 기준

두 에이전트 모두 `${CLAUDE_SKILL_DIR}/references/priorities.md`, `visual-rules.md`, `korean-copy.md`, `anti-ai-checklist.md`, `domains.md`를 기준으로 쓴다. 핵심만 적으면:

- **컬러:** 기본은 밝은 면이다. 네이비·슬레이트 배경, 인디고·보라 강조, Tailwind 기본 팔레트 그대로 같은 기본값을 피하고, 강조색은 의미가 있을 때만 작게 쓴다. 텍스트 대비는 WCAG AA 이상이고, `palette-check.mjs`에 실제로 겹쳐 쓰는 조합(`--text`, `--large`, `--ui`)을 넘겨 검사한다. 각 색에는 주제나 리서치 소스에서 나온 근거가 있어야 한다.
- **타이포그래피:** 서체는 주제에서 이유를 찾아 고른다. 모든 텍스트 스타일에 자간·행간을 직접 정하고 값마다 이유를 적는다. 한글은 자간을 많이 줄이지 않고(큰 제목 `0`~`-0.02em`), 큰 제목은 600~700 굵기와 `1.3`~`1.4` 행간에서 출발한다. "아주 굵은 제목 + 크게 줄인 자간 + 좁은 행간"은 생성형 화면의 기본값이다.
- **한국어 카피:** 실제 사용자가 하는 말로, 처음 보는 사람이 한 번에 이해하게, 사실과 맞게 쓴다. 자연스럽게 고치면서 기능·행동 주체·조건·시점·확실성을 바꾸지 않고, 뜻이 불분명하면 기능을 추측해 쓰지 않는다. 랜딩은 가치와 설득의 흐름을, 제품 화면은 위치·상태·다음 행동을 본다. `korean-copy.md`의 검수 순서로 걸러 내고, 고친 문장은 전후를 기록한다. 이 문서의 항목은 금지 목록이 아니라 "오해를 만드는가"를 묻는 기준이다.
- **목업:** `.design/mockups/<화면>-v<번호>.html` 독립 파일 하나, 인라인 CSS, 실제 카피와 현실적인 데이터, 상태 목록에서 "목업에서 확인"으로 정한 상태(보통 기본 상태와 방향 판단에 영향을 주는 상태 1~2개). 렌더링은 `${CLAUDE_SKILL_DIR}/scripts/render-mockup.sh`로 하고, 이 스크립트는 레퍼런스 URL 캡처에도 쓴다.

## 4. 시니어 리뷰와 개선: `ui:reviewer`

`ui:reviewer`를 띄우고 v1 HTML·PNG, 리서치 문서 경로를 넘긴다. 방향이 2개면 방향마다 하나씩 한 메시지에서 병렬로 띄운다. 리뷰어는:

- PNG를 직접 보고 첫인상 점검(예상 시선 흐름), 과업·위계·리듬·타이포·컬러·상태·분야 기준·접근성·AI 티·카피·리서치 반영을 리뷰한다. 지적마다 심각도(blocker/major/minor)와 근거, 수정 값을 붙인다. 상태는 계획의 상태 목록을 기준으로 본다.
- 결과를 **시각 확인 완료**(PNG로 판단할 수 있는 것)와 **구현 후 검증 필요**(키보드 이동, 포커스 복귀, 스크린리더 의미, 실제 과업 경로, 동작·전환)로 나눈다. 뒤쪽은 7단계에서 메인이 확인한다.
- blocker와 major를 반영한 v2를 만들고, 다시 찍어 v1과 비교해 해결됐는지 확인한다.

결과를 받으면 메인이 **v2 PNG와 리뷰 문서를 직접 확인한다.** 리뷰어가 "해결"이라고 한 blocker가 PNG에서 실제로 해결됐는지 본다. 남은 blocker가 있으면 리뷰어에게 한 번 더 맡긴다. **리뷰 왕복은 최대 2회다.** 그래도 남으면 남은 문제를 그대로 사용자에게 알린다.

리뷰어가 방향 자체가 틀렸다고 보고하면 고치지 말고, 그 의견을 5단계에서 사용자에게 함께 보여준다.

**기존 시스템 토큰의 대비 실패**는 리서치 문서나 리뷰 문서의 `## 시스템 대비 실패` 절로 올라온다. 이것 때문에 흐름을 멈추지 않는다. 5단계에서 함께 묻는다.

## 5. 사용자 검토 게이트

**사용자 승인 없이 구현으로 넘어가지 않는다.** 이 스킬에서 가장 중요한 멈춤 지점이다.

- 최종 목업(v2)이 `.design/mockups/`에 있다고 폴더와 파일 경로를 알려주고, **그 폴더에서 이미지를 열어 확인해 달라고 한다** (macOS면 `open <png>`로 열어줄 수 있다). 비교할 수 있게 v1 경로도 함께 준다. 그리고 다음을 짧게 설명한다:
  - 리서치에서 무엇을 봤는지: 참고한 제품·소스 몇 개와 각각에서 가져온 것, 채택하거나 일부러 쓰지 않은 트렌드
  - 이 디자인이 무엇을 노렸는지: 주제, 한 곳의 강조, 팔레트와 서체를 고른 이유
  - 시니어 리뷰에서 v1 → v2로 크게 바뀐 점과, 리뷰어가 사용자에게 판단을 넘긴 것
  - 레퍼런스를 받았다면 무엇을 가져오고 무엇을 가져오지 않았는지
- 그리고 묻는다. 선택지는 **이대로 구현 / 수정 후 다시 보기 / 다른 방향으로 다시**이고, 방향이 2개면 어느 쪽으로 갈지 묻는다.
- **시스템 대비 실패가 있으면** 같은 자리에서 따로 묻는다. 현재 목업, 실패한 조합(토큰 이름, 대비/기준, 화면에서 쓰인 곳), 리뷰어가 검토한 해결책을 보여준다. **공용 토큰 변경을 선택지에 올리기 전에 메인이 저장소에서 그 토큰의 사용처를 직접 확인한다.** 선택지는 `priorities.md` 4절 순서대로, 가능한 것만 올린다:
  - **기존 토큰 재조합:** 이 화면에서만 다른 기존 토큰을 쓴다. 공용 토큰과 다른 화면은 그대로다
  - **의미 토큰 추가:** 이 컴포넌트·역할에만 쓰는 토큰을 시스템 방식대로 추가한다. 공용 토큰과 다른 화면은 그대로다
  - **공용 토큰 변경:** 재조합과 의미 토큰으로 안 될 때만 올린다. 사용처 수와 영향받는 화면을 함께 보여준다
  - **이번에는 그대로 두기:** 승인 기록의 남은 문제에 적는다

  해결책을 고르면 구현 범위에 넣고, 목업도 바꾼 값으로 다시 찍어 보여준다. 공용 토큰 변경을 골랐으면 7단계에서 사용처 중 대표 화면을 함께 찍어 깨진 곳이 없는지 확인한다.
- **수정 후 다시 보기:** 요청 원문과 현재 버전을 `ui:reviewer`에게 넘겨 다음 버전(`-v3`)을 만든다. 색 하나, 문구 하나처럼 작은 수정이면 메인이 직접 고쳐 버전을 올리고 다시 찍어도 된다.
- **다른 방향으로 다시:** 사용자가 원하는 방향을 받아 3단계(`ui:researcher`)부터 다시 한다.
- 이전 버전 파일은 지우지 않는다. 비교할 때 필요하다.
- 승인되면 `.design/approved/<화면>.md`에 기록한다. 구현은 **이 기록과 승인된 목업을 기준으로** 한다.

  ```
  # <화면> 승인 기록 (<날짜>)
  - 승인 버전: .design/mockups/<화면>-v<n>.html (PNG: …)
  - 방향: 한 곳의 강조, 팔레트·서체 요약, 고른 방향과 고르지 않은 방향
  - 확인한 화면 폭: 1440 / 390 …
  - 상태: 목업에서 확인한 것 / 구현에서 확인할 것 / 해당 없음 (계획의 상태 목록 그대로)
  - 구현 후 검증 필요: 리뷰가 넘긴 항목
  - 남은 문제: 리뷰에서 반영하지 않은 지적, 사용자가 알고 넘어간 것
  - 수정 요청 이력: 무엇을 무엇으로 바꾸라고 했는지
  ```

- 수정 요청 이력과 고른·고르지 않은 방향은 8단계 선호 기록에도 쓴다.

사용자가 처음부터 "목업 없이 바로 구현해"라고 했을 때만 3~5단계를 건너뛴다. 이때도 리서치를 원하면 `ui:researcher`에게 리서치와 계획까지만 맡긴다.

**서브에이전트로 실행 중이라 사용자에게 물을 수 없으면,** 4단계까지만 하고 멈춘다. 최종 목업 경로와 설명을 보고해서 메인 에이전트가 승인을 받게 한다. 이미 승인된 목업을 넘겨받았으면 3~5단계를 건너뛰고 그 목업으로 6단계부터 한다.

## 6. 구현

- **승인된 목업을 그대로 옮긴다.** 구현하다가 목업과 달라져야 할 이유가 생기면(기술 제약, 기존 컴포넌트와의 충돌) 임의로 바꾸지 말고 이유와 함께 알린다.
- 프로젝트 스택의 관례(파일 위치, 컴포넌트 방식, 스타일 방식, 경로 별칭)대로 쓴다. 새 프로젝트면 요청에 맞는 가장 단순한 형태로 만든다.
- 계획의 토큰은 코드에서도 토큰으로 둔다 (CSS 변수, 테마 객체, Tailwind 설정). 컴포넌트마다 hex를 흩뿌리지 않는다.
- **실제 콘텐츠로 만든다.** 주제에 맞는 현실적인 데이터와 카피를 쓰고, lorem ipsum이나 "Feature 1/2/3"은 쓰지 않는다. 카피는 frontend-design의 글쓰기 원칙을 따른다.
- 승인 기록의 상태 목록에서 "구현에서 확인"인 상태까지 만든다. 목록에 없더라도 빈 상태·로딩·오류·긴 텍스트·숫자 자릿수가 커지는 경우가 이 화면에 생길 수 있으면 만들고 보고에 적는다. 행복한 경로만 예쁜 화면은 실제로 쓰이지 않는다.
- 품질 바닥선: 반응형(또는 기기 크기 대응), 키보드 포커스 표시, `prefers-reduced-motion` 존중, 터치 타깃, 대비.

## 7. 자기비평

- **스크린샷을 찍어 직접 본다.** 브라우저 도구(Claude in Chrome, 내장 브라우저, Playwright 등)가 있으면 데스크톱 폭과 모바일 폭에서 각각 확인한다. 스크린샷은 `.design/screenshots/<화면이름>-<desktop|mobile>.png`로 저장해서, 사용자가 목업과 나란히 열어볼 수 있게 한다. 모바일 앱이면 시뮬레이터 스크린샷이 있을 때만 확인하고, 없으면 사용자가 확인할 화면과 상태를 정리해 둔다.
- **승인된 목업과 나란히 놓고 비교한다.** 승인 기록에 적힌 화면 폭마다 찍고, 간격·크기·색·위계가 목업과 다르면 고친다.
- **핵심 과업 하나를 실제로 해 본다.** 브라우저 도구로 클릭·입력해 과업을 처음부터 끝까지 끝내 보고, 키보드만으로도 해 본다 (탭 순서, 포커스 표시, 모달·메뉴를 닫은 뒤 포커스 복귀). 승인 기록의 "구현 후 검증 필요" 항목과 "구현에서 확인" 상태를 하나씩 확인한다. 직접 할 수 없는 환경이면 사람이 확인할 목록으로 보고에 넘긴다.
- 볼 것:
  - 첫인상: 계획한 "한 곳의 강조"가 먼저 눈에 띄는가
  - 레퍼런스의 리듬·밀도가 살아 있는가
  - 체크리스트의 AI 티가 구현 과정에서 이유 없이 다시 들어오지 않았는가 (특히 컴포넌트 라이브러리 기본값으로 생기는 카드 나열, 같은 그림자, 대문자 라벨, 화살표 버튼)
  - 분야 기준을 지켰는가 (예: 대시보드의 숫자 정렬, 앱의 엄지 영역)
  - 계획한 서체·자간·행간·줄바꿈(`text-wrap`)이 코드에 그대로 들어갔는가 (컴포넌트 라이브러리 기본값이 덮어쓰지 않았는가)
  - 한국어 카피가 `korean-copy.md` 검수 순서를 통과하는가 (빈 상태·오류·토스트 문구까지 소리 내어 읽어 본다)
- 장식을 하나 뺀다. 빼서 나빠지지 않으면 빼둔다.

## 8. 보고

- **디자인 방향 요약:** 주제와 사용자, 한 곳의 강조, 팔레트(hex와 역할), 서체와 자간·행간
- **리서치에서 참고한 소스와 가져온 것, 일부러 가져오지 않은 것** (사용자 레퍼런스가 있었다면 그것도)
- **시니어 리뷰에서 바뀐 것:** v1 → 승인 버전까지 반영한 지적과 반영하지 않은 지적
- **AI 티 점검에서 바꾼 것:** 처음 계획에서 무엇을 왜 바꿨는지
- 팔레트 검사에서 경고가 나왔는데 유지한 색이 있으면 그 근거
- 승인 기록(`.design/approved/<화면>.md`)과 승인된 목업 경로, 구현이 목업과 다른 부분이 있다면 그 이유
- 핵심 과업을 실제로 해 본 결과와 "구현 후 검증 필요" 항목별 결과. 확인하지 못한 것은 확인하지 못했다고 적는다
- 이미지·문서 폴더 경로(`.design/research/`, `.design/reviews/`, `.design/mockups/`, `.design/approved/`, `.design/screenshots/`)와, 사용자가 열어서 확인할 파일
- 만든 파일과, 사람이 눈으로 확인해야 할 화면·상태

**선호 기록:** 이번 작업에서 사용자가 결과를 고치게 했거나, 선택지 중 하나를 골랐거나, 제안을 거절했거나, "앞으로는" 같은 지시를 했거나, 사용자의 행동에서 방식이 드러났다고 판단했고(예: Claude가 만든 결과를 사용자가 직접 같은 방향으로 고침) `prefs:learn` 스킬을 쓸 수 있으면, 5단계에서 적어 둔 선택과 수정 요청(무엇을 무엇으로 바꾸라고 했는지)를 요약해 넘겨 실행한다. 이번 작업에만 해당하는 내용은 넘기지 않는다.

## 하지 않을 것

- frontend-design 스킬을 건너뛰고 바로 코드 쓰기
- 목업 이미지와 사용자 승인 없이 구현하기
- 리서치 없이 기본값으로 목업 만들기, 열어 보지 않은 소스를 근거로 쓰기, 텍스트로만 읽은 소스에서 시각적 관찰을 가져오기
- 레퍼런스를 이유로 사용자 동의 없이 기존 디자인 시스템의 팔레트·타입 스케일 바꾸기
- 시니어 리뷰를 거치지 않은 목업을 사용자에게 최종안으로 보여주기
- 트렌드라는 이유만으로 AI 티 점검표에 걸리는 스타일 쓰기
- 기존 디자인 시스템을 사용자 동의 없이 갈아엎기
- 레퍼런스의 로고·고유 그래픽·카피를 그대로 복제하기
- 근거 없이 다크·네이비 테마, 보라 그라데이션, 글래스모피즘 쓰기
- 자간·행간을 브라우저 기본값에 맡기기
- 번역투나 말투가 섞인 한국어 카피 쓰기
- 스크린샷으로 확인하지 않고 "디자인 완료"라고 보고하기 (확인할 수 없는 환경이면 그 사실을 적는다)
