# UI 디자인

**가장 중요한 것은 디자인이다.** 동작하는 화면은 최소 조건일 뿐이다. 결과물은 "이 제품을 위해 사람이 내린 선택"으로 보여야 하고, 어느 프로젝트에나 나올 법한 기본값으로 보이면 실패다.

요청: `$ARGUMENTS`

## 0. frontend-design을 먼저 불러온다 (필수)

**가장 먼저 `frontend-design:frontend-design` 스킬을 호출한다.** 그 스킬의 원칙(주제에서 출발하기, 타이포그래피, AI 기본값 목록, 계획 → 검토 → 구현 → 자기비평 흐름, 카피 작성 원칙)이 이 스킬의 바탕이다. 이 스킬은 그 위에 레퍼런스, 분야, 컬러 정책을 더한다. 두 지침이 부딪히면 **사용자 요청 → 레퍼런스 → 선호 문서 → 이 스킬 → frontend-design** 순서로 우선한다.

스킬을 찾을 수 없으면 디자인을 시작하지 않는다. 사용자에게 `/plugin install frontend-design@claude-plugins-official` 설치를 안내하고 멈춘다.

## 1. 맥락 파악

- **사용자 선호를 읽는다:** `docs/PREFERENCES.md`(사용자 선호 문서)가 있으면 공통 절과 UI·디자인 절을 읽는다. `[확정]` 항목은 묻지 않고 기본값으로 따르고, `[관찰]` 항목은 선택지를 고를 때 먼저 고려하고, `[추정]` 항목은 다른 근거가 없을 때만 따르고 보고에 밝힌다. 이번 요청과 다르면 요청을 따른다. 선호 문서가 이 스킬의 컬러 정책과 다르면(예: 다크 테마를 확정) 선호 문서를 따른다.
- **분야를 정한다:** 대시보드·관리 도구 / 모바일 앱 / 웹 앱(SaaS 제품 화면) / 마케팅·랜딩 웹 / 커머스 / 콘텐츠·문서 중 무엇인가. 섞여 있으면 화면 단위로 정한다. 그다음 `${CLAUDE_SKILL_DIR}/references/domains.md`에서 해당 분야 절을 읽는다.
- **주제·사용자·핵심 과업을 한 줄씩 정한다.** 요청에 없으면 제안하고 확인받는다 (frontend-design 원칙).
- **기존 디자인 시스템을 확인한다:** 테마·토큰 파일(`theme/`, `tokens`, `tailwind.config.*`, CSS 변수), 컴포넌트 라이브러리, `CLAUDE.md`의 디자인 규칙.
  - **기존 시스템이 있으면 그 안에서 디자인한다.** 팔레트·타입 스케일을 새로 발명하지 않는다. 이 스킬의 차별화는 레이아웃·위계·밀도·카피·한 곳의 강조로 낸다.
  - 기존 시스템 자체가 아래 컬러 정책에 어긋나도(예: 네이비 다크 테마) **임의로 바꾸지 않는다.** 바꾸자는 제안만 근거와 함께 따로 한다.
  - 기존 시스템이 없거나 사용자가 새로 잡아 달라고 하면, 아래 컬러 정책으로 새로 만든다.
- **기술 스택을 확인한다:** 프레임워크, 스타일 방식(CSS Modules, Tailwind, styled, RN StyleSheet 등), 아이콘·폰트 로딩 방식. 결과물은 이 스택의 관례대로 쓴다.

## 2. 레퍼런스가 있으면: 레퍼런스 읽기

레퍼런스(이미지, 스크린샷, URL, Figma 캡처, 기존 제품명)가 주어졌으면 **디자인 계획보다 먼저** 분석한다.

- 이미지는 직접 본다. URL은 브라우저 도구가 있으면 스크린샷을 찍고, 없으면 WebFetch로 구조와 스타일 단서를 읽는다. 제품명만 받았으면 무엇을 참고하려는지 확인한다.
- 다음 축마다 레퍼런스가 **무엇을 하고 있는지** 구체적으로 적는다. "깔끔함" 같은 형용사가 아니라 관찰한 사실을 쓴다:

| 축 | 관찰할 것 |
|---|---|
| 레이아웃 | 그리드, 여백 리듬, 정렬 축, 정보 밀도, 섹션 전환 방식 |
| 타이포 | 서체 분류(휴머니스트 산세리프, 디돈 세리프 등), 크기 대비, 굵기, 자간, 줄 길이 |
| 컬러 | 대략적인 hex 값, 면적 비율(배경:면:강조), 채도 수준, 강조색을 쓰는 곳 |
| 형태 | 모서리 반경 체계, 테두리·그림자·면 분리 방식, 아이콘 스타일 |
| 이미지·그래픽 | 사진·일러스트·데이터 그래픽의 비중과 처리 방식 |
| 모션·인터랙션 | 보이면 적는다 |
| 카피 톤 | 문장 길이, 존댓말·반말, 전문 용어 수준 |

- **가져올 것과 가져오지 않을 것을 나눈다.** 레퍼런스에서 가져오는 것은 리듬·밀도·위계·톤·컬러 감각이다. 로고, 고유 일러스트, 브랜드 카피, 특정 서비스의 화면 배치를 그대로 복제하지 않는다. 레퍼런스가 여러 개면 축마다 어느 레퍼런스를 따를지 정한다 (예: "레이아웃은 A, 컬러 감각은 B").
- 레퍼런스가 이 스킬의 컬러 정책과 다르면(예: 레퍼런스가 다크 테마) **레퍼런스를 따른다.** 사용자가 직접 고른 방향이기 때문이다.

## 3. 디자인 계획 (frontend-design의 첫 번째 패스)

frontend-design이 정한 계획 형식(컬러 4~6개 hex, 타입, 레이아웃 ASCII 와이어프레임, 원칙)으로 계획을 세운다. 여기에 다음을 더한다:

- **분야 기준:** `domains.md`에서 이 분야의 필수 요소와 이 분야 특유의 AI 티를 계획에 반영한다.
- **컬러 근거:** 각 색이 **왜 이 주제에 맞는지** 한 줄씩 쓴다. 근거는 주제의 재료·산업·현장·사용 환경에서 찾는다. "모던해 보여서", "신뢰감" 같은 근거는 근거가 아니다.
- **레퍼런스 대응:** 레퍼런스가 있으면 계획의 각 축이 레퍼런스의 어느 관찰에서 왔는지 적는다.
- **한 곳의 강조:** 이 화면에서 기억에 남을 단 하나의 요소가 무엇인지 정한다. 나머지는 조용하게 둔다.

### 컬러 정책 (기존 시스템이나 레퍼런스가 따로 정하지 않았을 때)

- **기본은 밝은 면이다.** 다크 테마는 사용자가 요청했거나, 그 분야의 실제 관례일 때만 쓴다. 영상·사진 편집 도구, 트레이딩 터미널, 야간 관제, 극장·공연 콘텐츠 등이 그런 분야다.
- **피할 기본값:**
  - 네이비·슬레이트 계열 배경 (`#0F172A`, `#1E293B`, `#111827`, `#0B1120` 근처)
  - 인디고·보라 강조와 보라→파랑 그라데이션 (`#6366F1`, `#8B5CF6`, `#7C3AED` 근처)
  - 다크 배경에 형광 글로우, 글래스모피즘
  - Tailwind 기본 팔레트를 그대로 쓴 조합 (`slate`/`gray`/`zinc` + `blue-500`/`indigo-600`)
  - frontend-design이 꼽은 크림+테라코타(`#F4F1EA`/`#D97757` 근처), 검정+형광 초록·주홍
- **중립색에도 성격을 준다.** 회색은 순수 회색이나 파란 슬레이트 대신 주조색 쪽으로 아주 살짝 기울인다.
- **강조색은 면적을 작게 쓴다.** 강조색이 의미(주요 행동, 상태, 선택)를 가질 때만 칠한다.
- **데이터 색은 브랜드 색과 따로 설계한다.** 차트 범주색은 구분이 잘 되고 색각 이상에서도 읽히게 하며, 상태색(성공·경고·오류)은 주조색과 겹치지 않게 한다.
- 텍스트 대비는 WCAG AA 이상을 지킨다 (본문 4.5:1, 큰 글자·UI 요소 3:1).

### 계획 검사

계획을 확정하기 전에 두 가지를 돌린다:

1. **팔레트 검사:** 계획한 hex 값을 넘겨 기본값 패턴과 대비를 확인한다.
   ```bash
   node "${CLAUDE_SKILL_DIR}/scripts/palette-check.mjs" --bg "#F2F4F0" --fg "#1F2421" "#2F6B4F" "#E8B04B" "#C8553D"
   ```
   `--bg`는 주 배경, `--fg`는 본문 글자색이다. 경고가 나온 색은 근거가 있으면 보고에 근거를 적고 유지하고, 근거가 없으면 바꾼다.
2. **AI 티 점검:** `${CLAUDE_SKILL_DIR}/references/anti-ai-checklist.md`를 계획에 대고 하나씩 확인한다. 걸린 항목은 바꾸고, **무엇을 왜 바꿨는지** 적는다. 비슷한 요청을 받았을 때 다른 화면에서도 똑같이 나올 계획이면 다시 세운다.

## 4. 목업 이미지 산출 (코드보다 먼저)

**계획이 확정돼도 바로 구현하지 않는다.** 먼저 목업을 이미지로 만들어 사용자에게 보여주고, 승인을 받은 뒤에 구현한다. 코드로 짠 다음에 방향을 바꾸면 비용이 몇 배로 든다.

### 목업 만들기

- 목업은 **프로젝트 코드와 분리된 독립 HTML 파일 하나**로 만든다. 저장 위치는 `<저장소 루트>/.design/mockups/<화면이름>-v<번호>.html`이다. 저장소가 아니면 현재 디렉터리 아래에 둔다.
  - **이 스킬이 만드는 이미지는 모두 `<저장소 루트>/.design/` 아래에 둔다.** 목업은 `mockups/`, 구현 스크린샷은 `screenshots/`에 둔다. 임시 디렉터리나 스크래치 디렉터리에 두지 않는다. 사용자가 그 폴더를 열어 직접 확인할 수 있어야 한다.
  - `.design/`이 `.gitignore`에 없으면 추가할지 사용자에게 묻는다.
- 목업은 그리기 위한 것이다. 인라인 CSS 하나로 쓰고, 프레임워크·빌드·JS 로직은 쓰지 않는다. 웹폰트는 `<link>`로 불러와도 된다.
- **충실도는 높게 잡는다.** 계획의 실제 팔레트·서체·간격·모서리·실제 카피와 현실적인 데이터를 그대로 쓴다. 회색 박스 와이어프레임은 목업이 아니다. 아이콘은 인라인 SVG나 단순한 도형으로 대신해도 된다.
- 한 이미지 안에 판단에 필요한 상태를 함께 그린다: 기본 상태와, 이 화면에서 중요한 상태 1~2개(빈 상태, 오류, 선택됨, 로딩 등).
- 한글 화면이면 `word-break: keep-all`을 넣어 단어 중간에서 줄이 바뀌지 않게 한다.
- 레퍼런스가 없고 방향이 열려 있으면, **서로 확실히 다른 방향 2개**를 만들어 비교하게 해도 된다. 색만 바꾼 변형은 다른 방향이 아니다.

### 이미지로 렌더링하기

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/render-mockup.sh" .design/mockups/<화면>-v1.html .design/mockups/<화면>-v1-desktop.png 1440 900
bash "${CLAUDE_SKILL_DIR}/scripts/render-mockup.sh" .design/mockups/<화면>-v1.html .design/mockups/<화면>-v1-mobile.png 390 844
```

- 분야에 맞는 폭으로 찍는다. 웹은 데스크톱과 모바일 둘 다, 대시보드는 1440(필요하면 1920), 모바일 앱은 390×844 하나로 찍는다.
- Bash `timeout`은 `300000`으로 준다. 처음 실행할 때 브라우저를 내려받을 수 있다.
- 렌더링에 실패하면(종료 코드 127) 사용자에게 HTML 파일 경로를 알려 브라우저로 직접 열어보게 하고, 이미지 검토와 같은 방식으로 승인을 받는다.

### 내가 먼저 본다

렌더링한 PNG를 **직접 열어 본다.** 사용자에게 보여주기 전에 다음을 확인하고, 걸리면 목업을 고쳐 다시 찍는다:
- 깨진 레이아웃, 넘친 텍스트, 줄바꿈 이상, 로딩되지 않은 폰트
- 계획한 "한 곳의 강조"가 첫눈에 보이는가
- `anti-ai-checklist.md`의 항목이 목업에 다시 들어오지 않았는가

## 5. 사용자 검토 게이트

**사용자 승인 없이 구현으로 넘어가지 않는다.** 이 스킬에서 가장 중요한 멈춤 지점이다.

- 이미지가 `.design/mockups/`에 있다고 폴더와 파일 경로를 알려주고, **그 폴더에서 이미지를 열어 확인해 달라고 한다** (macOS면 `open <png>`로 열어줄 수 있다). 그리고 다음을 짧게 설명한다:
  - 이 디자인이 무엇을 노렸는지: 주제, 한 곳의 강조, 팔레트와 서체를 고른 이유
  - 레퍼런스가 있었다면 무엇을 가져오고 무엇을 가져오지 않았는지
- 그리고 묻는다. 선택지는 **이대로 구현 / 수정 후 다시 보기 / 다른 방향으로 다시**이고, 방향이 2개면 어느 쪽으로 갈지 묻는다.
- 수정 요청을 받으면 목업 버전을 올려(`-v2`) 다시 렌더링하고 다시 묻는다. 이전 버전 파일은 지우지 않는다. 비교할 때 필요하다.
- 승인된 버전을 기록해 둔다. 구현은 **승인된 목업을 기준으로** 한다.
- 사용자가 고른 방향, 고르지 않은 방향, 수정 요청의 내용을 적어 둔다. 8단계에서 선호 기록에 쓴다.

사용자가 처음부터 "목업 없이 바로 구현해"라고 했을 때만 이 단계를 건너뛴다.

**서브에이전트로 실행 중이라 사용자에게 물을 수 없으면,** 4단계까지만 하고 멈춘다. 목업 경로와 설명을 보고해서 메인 에이전트가 승인을 받게 한다. 이미 승인된 목업을 넘겨받았으면 4·5단계를 건너뛰고 그 목업으로 6단계부터 한다.

## 6. 구현

- **승인된 목업을 그대로 옮긴다.** 구현하다가 목업과 달라져야 할 이유가 생기면(기술 제약, 기존 컴포넌트와의 충돌) 임의로 바꾸지 말고 이유와 함께 알린다.
- 프로젝트 스택의 관례(파일 위치, 컴포넌트 방식, 스타일 방식, 경로 별칭)대로 쓴다. 새 프로젝트면 요청에 맞는 가장 단순한 형태로 만든다.
- 계획의 토큰은 코드에서도 토큰으로 둔다 (CSS 변수, 테마 객체, Tailwind 설정). 컴포넌트마다 hex를 흩뿌리지 않는다.
- **실제 콘텐츠로 만든다.** 주제에 맞는 현실적인 데이터와 카피를 쓰고, lorem ipsum이나 "Feature 1/2/3"은 쓰지 않는다. 카피는 frontend-design의 글쓰기 원칙을 따른다.
- 빈 상태·로딩·오류·긴 텍스트·숫자 자릿수가 커지는 경우까지 디자인한다. 행복한 경로만 예쁜 화면은 실제로 쓰이지 않는다.
- 품질 바닥선: 반응형(또는 기기 크기 대응), 키보드 포커스 표시, `prefers-reduced-motion` 존중, 터치 타깃, 대비.

## 7. 자기비평

- **스크린샷을 찍어 직접 본다.** 브라우저 도구(Claude in Chrome, 내장 브라우저, Playwright 등)가 있으면 데스크톱 폭과 모바일 폭에서 각각 확인한다. 스크린샷은 `.design/screenshots/<화면이름>-<desktop|mobile>.png`로 저장해서, 사용자가 목업과 나란히 열어볼 수 있게 한다. 모바일 앱이면 시뮬레이터 스크린샷이 있을 때만 확인하고, 없으면 사용자가 확인할 화면과 상태를 정리해 둔다.
- **승인된 목업과 나란히 놓고 비교한다.** 간격·크기·색·위계가 목업과 다르면 고친다.
- 볼 것:
  - 첫눈에 시선이 계획한 "한 곳의 강조"로 가는가
  - 레퍼런스의 리듬·밀도가 살아 있는가
  - 체크리스트의 AI 티가 구현 과정에서 다시 들어오지 않았는가 (특히 카드 나열, 동일한 그림자, 대문자 라벨, 화살표 버튼)
  - 분야 기준을 지켰는가 (예: 대시보드의 숫자 정렬, 앱의 엄지 영역)
- 장식을 하나 뺀다. 빼서 나빠지지 않으면 빼둔다.

## 8. 보고

- **디자인 방향 요약:** 주제와 사용자, 한 곳의 강조, 팔레트(hex와 역할), 서체
- **레퍼런스에서 가져온 것과 일부러 가져오지 않은 것** (레퍼런스가 있었다면)
- **AI 티 점검에서 바꾼 것:** 처음 계획에서 무엇을 왜 바꿨는지
- 팔레트 검사에서 경고가 나왔는데 유지한 색이 있으면 그 근거
- 승인된 목업 경로와, 구현이 목업과 다른 부분이 있다면 그 이유
- 이미지 폴더 경로(`.design/mockups/`, `.design/screenshots/`)와, 사용자가 열어서 확인할 파일
- 만든 파일과, 사람이 눈으로 확인해야 할 화면·상태

**선호 기록:** 이번 작업에서 사용자가 결과를 고치게 했거나, 선택지 중 하나를 골랐거나, 제안을 거절했거나, "앞으로는" 같은 지시를 했거나, 사용자의 행동에서 방식이 드러났다고 판단했고(예: Claude가 만든 결과를 사용자가 직접 같은 방향으로 고침) `prefs:learn` 스킬을 쓸 수 있으면, 5단계에서 적어 둔 선택과 수정 요청(무엇을 무엇으로 바꾸라고 했는지)를 요약해 넘겨 실행한다. 이번 작업에만 해당하는 내용은 넘기지 않는다.

## 하지 않을 것

- frontend-design 스킬을 건너뛰고 바로 코드 쓰기
- 목업 이미지와 사용자 승인 없이 구현하기
- 기존 디자인 시스템을 사용자 동의 없이 갈아엎기
- 레퍼런스의 로고·고유 그래픽·카피를 그대로 복제하기
- 근거 없이 다크·네이비 테마, 보라 그라데이션, 글래스모피즘 쓰기
- 스크린샷으로 확인하지 않고 "디자인 완료"라고 보고하기 (확인할 수 없는 환경이면 그 사실을 적는다)
