# 한국어 카피

화면의 한국어는 **이 제품의 실제 사용자가 하는 말로, 처음 보는 사람이 한 번에 이해하게** 쓴다. 그리고 **사실과 맞게** 쓴다. 자연스럽지만 기능을 잘못 알려주는 문장은 어색한 문장보다 나쁘다.

ui:design의 계획(카피 초안), 목업 자체 점검, 시니어 리뷰, 구현 후 자기비평에서 읽는다. 문서 끝의 **검수 순서**를 매번 거친다.

이 문서의 항목은 금지 목록이 아니다. 판단 기준은 **오해를 만드는가, 읽기를 막는가**다. 아래 표현이 불필요하면 피하고, 의미와 맥락에 맞으면 쓴다. 억지로 고친 문장이 원래 문장보다 부정확하면 고치지 않는다.

## 1. 의미를 지킨다 (가장 먼저)

**문장을 다듬으면서 기능, 행동 주체, 조건, 시점, 확실성의 정도를 바꾸지 않는다.** 원래 없던 기능이나 약속(알림, 처리 기한, 자동 처리)을 덧붙이지도 않는다. 원래 의미가 불분명하면 기능을 추측해 쓰지 않는다. 기획·요청·기능 설명에서 확인하고, 확인할 수 없으면 "확인 필요"로 남겨 보고한다.

| 바뀌면 안 되는 것 | 잘못 고친 예 | 맞게 고친 예 |
|---|---|---|
| 기능 | "보고서가 자동으로 생성되어 발송됩니다" → "소장님이 확인하고 보냅니다" (자동 발송이 수동 발송으로 바뀜) | 자동 발송 기능이면 "보고서를 자동으로 만들어 보냅니다" |
| 행동 주체 | "관리자가 승인하면 공개됩니다" → "승인하면 공개됩니다" (읽는 사람이 승인하는 것처럼 읽힘) | "관리자가 승인하면 공개됩니다" (그대로 둔다) |
| 조건 | "결제를 완료하면 바로 시작할 수 있습니다" → "바로 시작할 수 있습니다" | 조건을 남긴다 |
| 시점 | "다음 알림부터 적용됩니다" → "바로 적용됩니다" | 시점을 남긴다 |
| 확실성 | "AI로 업무를 자동화하는 것이 가능합니다" → "AI가 업무를 대신 처리합니다" (가능 → 확정) | "AI로 업무를 자동화할 수 있습니다" |
| 범위 | "업무를 자동화합니다" → "반복 업무를 자동화합니다" (범위를 좁힘) | 범위가 확인된 경우에만 좁힌다 |

원문에 구체적인 뜻이 없는 문장("당신의 하루를 더 스마트하게", "데이터가 답을 알려줍니다")은 표현만 바꿔서 해결되지 않는다. 제품이 실제로 무엇을 해 주는지 확인해서 그 내용을 쓴다. 확인할 수 없으면 기능을 지어내지 말고 "무엇이 달라지는지 확인 필요"로 넘긴다.

## 2. 화면 종류에 따라 기준이 다르다

| | 랜딩·마케팅 화면 | 제품 화면 (설정, 관리, 목록, 입력, 상태 안내) |
|---|---|---|
| 독자가 묻는 것 | 이게 뭔가, 나한테 왜 필요한가, 믿어도 되나 | 지금 어디에 있나, 지금 상태는 무엇인가, 다음에 무엇을 하면 되나 |
| 제목 | 방문자가 얻는 것을 문장으로 말할 수 있다 | 화면·영역의 이름이면 충분하다. "알림 설정", "결제 내역" 같은 명사 제목이 자연스럽다 |
| 흐름 | 섹션이 설득의 순서로 이어진다 | 위치 → 상태 → 행동이 분명하다. 설득하지 않는다 |
| 말의 양 | 가치를 설명할 만큼 | 행동을 판단하는 데 필요한 만큼. 대상·조건·결과는 빠뜨리지 않고 중복 설명을 줄인다 |

한 화면 안에 둘이 섞여 있으면(예: 제품 안의 업그레이드 안내) 영역마다 기준을 정한다.

## 3. 상태와 안내 문구 (제품 화면)

| 기준 | 모호하거나 틀린 예 | 고친 예 |
|---|---|---|
| **지시 대상을 분명히 한다** | "이 항목을 변경하면 적용됩니다" | "알림 시간을 바꾸면 다음 알림부터 적용됩니다" |
| **상태와 행동 결과를 구분한다** | 요청만 접수했는데 "환불이 완료됐습니다" | "환불 요청을 접수했습니다" (처리 결과를 알려 주는 기능이 확인된 경우에만 "처리되면 알려 드립니다"를 덧붙인다) |
| | 예약만 했는데 "메시지를 보냈습니다" | "11월 12일 오전 9시에 보내도록 예약했습니다" |
| **오류는 현상과 다음 행동을 알려준다** | "오류가 발생했습니다" | "파일을 올리지 못했습니다. 다시 시도해 주세요" |
| **재시도 안내는 안전한 경우에만 쓴다** | 결제 응답이 끊겼는데 "다시 시도해 주세요" | "결제 결과를 확인하지 못했습니다. 다시 결제하기 전에 결제 내역을 확인해 주세요" (처리 결과가 불분명한 결제·전송·등록은 중복 실행 가능성을 확인하고, 필요하면 내역 확인을 먼저 안내한다) |
| **오류 원인은 확인된 경우에만 쓴다** | 원인을 모르는데 "인터넷 연결을 확인해 주세요" | "파일을 올리지 못했습니다. 다시 시도해 주세요" (원인이 네트워크로 확인되면 그때 연결 확인을 안내한다) |
| **빈 상태를 종류별로 나눈다** | 모든 경우에 "데이터가 없습니다" | 처음: "아직 등록한 작업이 없습니다" + 등록 버튼 / 검색·필터: "검색 조건에 맞는 작업이 없습니다" + 조건 초기화 / 권한: "이 작업을 볼 권한이 없습니다" + 요청 방법 |
| **확인 대화상자의 버튼은 동작 이름으로** | "삭제할까요?" [취소] [확인] | "삭제할까요?" [취소] [삭제] |

결과 상태를 알리는 문구는 피동이 자연스럽다. "저장되었습니다", "연결이 끊어졌습니다"처럼 무엇이 어떻게 되었는지가 중요하고 행동 주체가 분명할 때는 고치지 않는다.

## 4. 어색한 문장

| 문제 | 어색한 예 | 고친 예 |
|---|---|---|
| **번역투** | "AI를 통해 업무를 자동화하는 것이 가능합니다" | "AI로 업무를 자동화할 수 있습니다" |
| | "로그인을 진행해 주세요" | "로그인해 주세요" |
| **추상 명사·사물이 주어인 비유** | "현장에서 말한 하루가 건축주 보고서가 됩니다" | "말로 남긴 메모를 건축주에게 보낼 공정 보고서로 정리해 드립니다" |
| **불필요한 피동** (누가 하는지 흐려져 오해가 생김) | "요청하신 내용이 검토될 예정입니다" | "담당자가 3일 안에 검토합니다" (담당자와 기한이 확인된 경우) |
| **정보 없는 문장** | "한 화면에서 위에서 아래로 읽힙니다" | 지운다. 또는 실제로 알려줄 것을 쓴다: "오늘 한 일, 사진, 내일 일정이 순서대로 한 화면에 나옵니다" |
| **수식 관계가 불분명함** (수식어가 길거나 겹쳐 무엇을 꾸미는지 한 번에 알기 어려움. 수식어 개수 자체는 문제가 아니다) | "장갑을 벗지 않고 눌러서 말하는 버튼 하나가 전부입니다" | "장갑을 낀 채로 버튼 하나만 누르고 말하면 됩니다" |
| **명사 나열** | "데이터 분석 결과 확인 기능" | "분석 결과 보기" |
| **과한 높임·사물 존대** | "주문하신 상품이 나오셨습니다", "사용하실 수 있으십니다" | "주문하신 상품이 나왔습니다", "사용하실 수 있습니다" |
| **조사·어미 어긋남** | "회원 가입 시 혜택을 드립니다를 확인하세요" | "가입하면 받는 혜택을 확인하세요" |

## 5. 어렵게 쓴 문장

- **한자어 명사보다 동사가 읽기 쉽다.** "발송 처리 완료" → "보냈습니다", "검토 후 승인 필요" → "확인한 뒤 승인해야 합니다". 표·배지처럼 짧은 상태 표시는 명사형("발송 완료")이 더 맞을 수 있다.
- **전문 용어는 그 분야 사용자가 실제로 쓰는 말만 쓴다.** 업계 사람이 쓰는 말("양생", "공정")은 살리고, 만든 사람만 아는 시스템 용어("워크플로", "인스턴스", "파이프라인")는 사용자 말로 바꾼다. 사용자가 개발자라면 그 말이 사용자 말이다.
- **지나치게 줄이지 않는다.** 짧게 쓰려다 뜻이 사라진 문장은 풀어 쓴다. 풀어 쓸 때도 1절의 의미를 지킨다.
  - "틀린 곳은 말한 문장 옆에서 고칩니다" → "잘못 받아쓴 부분은 녹음 원문과 나란히 보면서 고칠 수 있습니다" (받아쓰기 오류를 고치는 기능일 때)
- **문장 길이는 검토 신호다.** 40자를 넘으면 정보가 둘 이상 들어 있지 않은지, 60자를 넘으면 나눌 수 있는지 본다. 나누면 뜻이 흐려지거나 조건이 떨어져 나가면 그대로 둔다.
- **이중 부정은 더 단순한 말이 있으면 바꾼다.** "확인하지 않으면 보내지 않습니다" → "확인한 보고서만 보냅니다". 예외를 강조해야 하는 안전·법적 안내처럼 부정이 더 정확하면 둔다.
- **구체적으로 말한다.** "빠르게", "간편하게" 대신 실제로 무엇이 줄어드는지 쓴다. 근거 없는 숫자는 지어내지 않는다. 모르면 숫자 없이 구체적인 장면으로 쓴다.

## 6. 흐름

- **문장끼리 이어진다.** 뒤 문장은 앞 문장을 받아서 이유·방법·예를 보탠다. 같은 말을 표현만 바꿔 되풀이하지 않는다.
- **용어를 하나로 정한다.** 같은 대상을 "보고서", "리포트", "일보"로 섞어 부르지 않는다. 버튼 이름과 그 버튼이 여는 화면의 제목을 맞춘다.
- **랜딩·마케팅 화면:**
  - 제목은 방문자가 얻는 것을 말하고, 본문은 그것이 어떻게 되는지, 왜 믿을 수 있는지를 보탠다. 본문이 제목을 다시 풀어 말하기만 하면 본문을 지운다.
  - 섹션 순서는 방문자가 품는 질문 순서를 따른다. 예: 이게 뭔가 → 나한테 무슨 도움이 되나 → 어떻게 하나 → 믿어도 되나 → 얼마인가, 어떻게 시작하나. 템플릿 순서(문제 → 해결 → 기능 3개 → 후기 → CTA)를 그대로 쓰지 않는다.
- **제품 화면:** 화면 제목 → 현재 상태 → 할 수 있는 행동 순으로 읽혀야 한다. 안내 문구는 행동을 판단하는 데 필요한 대상·조건·결과를 담고, 중복 설명을 줄인다. 삭제·결제처럼 되돌리기 어려운 행동은 결과 설명이 길어져도 빠뜨리지 않는다.

## 7. AI가 쓴 티가 나는 한국어 (주로 랜딩·마케팅 화면)

하나만 있다고 바로 문제는 아니다. **같은 화면에 여럿 겹치거나, 구체적인 내용이 있어야 할 자리를 차지하고 있으면** 고친다.

- **상투어:** 손쉽게, 간편하게, 한눈에, 스마트하게, 새로운 기준, 그 이상의, 단 하나의, ~의 시작, 지금 바로, 놓치지 마세요, 경험해 보세요, 혁신적인, 차세대, 완벽한, 모든 것을 한곳에
- **반복 리듬:**
  - 모든 섹션이 "단정하는 평서문 제목 + 회색 설명 두 줄" 구조로 반복된다
  - 셋씩 나열하는 대구가 계속된다 ("읽고, 고치고, 보냅니다")
  - "~가 아닙니다. ~입니다" 대조나 "~하지 않습니다" 부정 단정이 연달아 나온다
  - "~면 됩니다", "~가 전부입니다", "~면 끝"처럼 단순함을 과장하는 끝맺음이 반복된다
- **명사로 끝나는 문장 남발:** "보고서까지 한 번에." "현장의 모든 기록을." 짧은 표어는 한 화면에 하나면 충분하다.
- **영어식 문장 부호:** 콜론(`:`)이나 줄표(`—`)로 문장을 잇는 구조, 따옴표로 단어를 강조하는 습관.

## 8. 말투와 표기

- **말투를 하나로 맞춘다.** 한 화면 안에서 "~합니다"와 "~해요"를 섞지 않는다. 사용자와 분야에 맞춰 고른다. 업무 도구·공공·금융은 "~합니다", 일상 소비자 서비스는 "~해요"가 흔하다. 기존 제품의 말투가 있으면 그것을 따른다.
- **버튼은 동작을, 메뉴는 이동할 곳을 분명히 말한다.** 메뉴는 "설정", "결제 내역"처럼 도착할 화면의 이름으로 쓰고, 그 화면의 제목과 맞춘다. 버튼은 명사형("저장")이나 동사형("저장하기") 중 하나로 통일한다. "확인", "제출"은 무슨 일이 일어나는지 맥락으로 분명할 때(양식의 "제출", 알림만 닫는 "확인") 써도 된다. 맥락이 없으면 동작 이름을 쓴다.
- **2인칭은 보통 필요 없다.** 한국어 UI는 주어를 생략하는 게 자연스럽다. "당신의", "귀하의"가 어색하면 빼거나 그 분야의 호칭("소장님", "사장님")이나 "내 ~"("내 정보")를 쓴다. 브랜드 말투로 정한 경우에는 쓴다.
- **변수 자리의 조사를 처리한다.** "을(를)"을 그대로 노출하지 않는다. 받침에 따라 조사를 고르거나, 조사가 필요 없게 문장을 바꾼다.
- **띄어쓰기·맞춤법·표기를 지킨다.** 숫자는 천 단위 쉼표, 단위는 붙여 쓰고("3개", "1,200원"), 날짜·시간 형식을 한 화면 안에서 통일한다.
- **외래어·영어는 그 분야 사용자가 실제로 쓰는 말만 쓴다.**
- **문장 부호를 아낀다.** 느낌표, 물결표, 말줄임표는 그 제품의 말투일 때만 쓴다.

## 검수 순서

카피를 확정할 때, 목업을 점검할 때, 리뷰할 때 이 순서로 본다.

1. **화면 종류를 정한다:** 영역마다 랜딩·마케팅인지 제품 화면인지 정한다 (2절).
2. **흐름 읽기:**
   - 랜딩·마케팅: 제목(히어로, 섹션 제목, 버튼)만 위에서부터 이어 읽는다. 그것만으로 무엇이고 왜 필요한지 이야기가 되는지, 리듬이 단조롭게 반복되지 않는지 본다.
   - 제품 화면: 화면 제목, 상태 표시, 버튼만 읽는다. 지금 어디에서 어떤 상태이고 다음에 무엇을 하면 되는지 알 수 있는지 본다. 빈 상태·오류·확인 대화상자 문구까지 본다.
3. **소리 내어 읽기:** 모든 문장을 실제 사용자에게 말하듯 읽는다. 입에서 걸리는 문장, 숨이 차는 문장을 표시한다.
4. **문장마다 묻는다:**
   - 누가 무엇을 하는지 분명한가 (불필요한 피동, 추상 주어, 비유)
   - 처음 보는 사람이 한 번에 이해하는가 (압축, 전문 용어, 수식 관계, 길이)
   - 지워도 잃는 정보가 없는가 (있으나 마나 한 문장이면 지운다)
   - 이 제품의 실제 사용자가 이렇게 말하는가 (번역투, 상투어, 말투)
   - 사용자가 지금 상태와 다음 행동을 정확히 알 수 있는가 (지시 대상, 상태와 결과, 오류 안내, 재시도가 안전한지)
   - 기능이나 약속을 새로 만들지 않았는가 (알림, 처리 기한, 자동 처리처럼 확인되지 않은 약속)
5. **7절의 티를 센다:** 같은 리듬이나 상투어가 여러 번 나오면 고친다.
6. **고친 문장을 원래 문장과 대조한다:** 자연스럽게 고치는 과정에서 원래 기능이나 사실(주체, 조건, 시점, 확실성, 범위)을 바꾸지 않았는가. 바뀌었으면 되돌리거나, 바뀐 쪽이 맞다는 근거를 확인한다.
7. **고친 문장은 전후를 기록한다.** 리서치 문서·리뷰 문서·보고에 "원래 문장 → 고친 문장"으로 남기고, 의미를 확인하지 못한 문장은 "확인 필요"로 따로 적는다.
