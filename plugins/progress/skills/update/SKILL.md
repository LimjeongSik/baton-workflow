# 진행 문서 관리 (docs/PROGRESS.md)

진행 문서는 **다음 세션의 Claude가 작업 전에 읽는 문서**다. 사람에게 보여주는 홍보 문서가 아니다. 코드만 봐서는 알 수 없는 것을 담는다: 지금 어디까지 왔는지, 왜 그렇게 정했는지, 무엇이 검증됐는지, 다음에 뭘 할지.

**문서는 이력 저장소가 아니다.** 과거 기록은 git이 갖고 있다. 이 문서는 "지금 상태"와 "최근 흐름"만 짧게 유지한다. 매번 읽히는 문서라서 길어질수록 모든 세션의 비용이 늘어난다.

경로는 기본 `docs/PROGRESS.md`다. 환경 변수 `DOCS_PROGRESS_PATH`가 있으면 그 경로(저장소 루트 기준)를 쓴다.

## 원칙

- **확인한 것만 적는다.** 검사 결과는 실제로 실행하고 적는다. 추측이나 계획을 완료로 쓰지 않는다.
- **코드에서 바로 보이는 것은 중복하지 않는다.** 파일 목록을 나열하지 않는다. 구조는 계층과 역할만 적는다.
- **날짜는 절대 날짜(`YYYY-MM-DD`)로 쓴다.** "어제", "최근" 같은 상대 표현은 쓰지 않는다. 오늘 날짜는 `date +%F`로 확인한다.
- **실패를 숨기지 않는다.** 검사가 깨졌으면 깨졌다고 적는다.
- 섹션 8개는 고정이다. 순서와 제목을 바꾸지 않는다. 내용이 없으면 `- 없음`이라고 적는다.
- **문서 전체는 대략 200줄 안으로 유지한다.** 넘치면 아래 "정리 규칙"을 먼저 적용한다.

## 갱신 절차

1. 진행 문서를 읽는다. 없거나 인자가 `init`이면 아래 템플릿으로 새로 만든다. 처음 만들 때는 README, `CLAUDE.md`, 매니페스트, `git log --oneline -30`으로 1·2·3·4·8절을 채운다.
2. 마지막 갱신 뒤로 무엇이 바뀌었는지 파악한다:
   ```bash
   git log --format='%h %ad %s' --date=short --since='<최종 갱신일> 00:00'
   git status --short
   ```
   이번 세션에서 한 작업은 대화 맥락에서 가져온다. 이미 문서에 반영된 작업은 다시 적지 않는다.
3. 달라진 섹션만 고친다. 전체를 다시 쓰지 않는다.
4. 7절(마지막 검증)은 반드시 실제로 실행하고 결과를 적는다. 검사 명령은 `CLAUDE.md` / `AGENTS.md` → `package.json` 스크립트(lockfile로 패키지 매니저 판단) → 표준 도구 순서로 찾고, 지어내지 않는다.
5. 끝난 항목은 8절에서 빼고 3절·5절에 반영한다. 8절에 남겨두지 않는다.
6. 상단의 `최종 갱신` 날짜를 오늘로 바꾼다. **이 줄은 세션 시작 훅이 문서가 오래됐는지 판단하는 기준이다.** 형식(`최종 갱신: YYYY-MM-DD`)을 바꾸지 않는다.
7. "정리 규칙"을 적용한다.

## 섹션별 작성 기준

**1. 프로젝트 진행사항:** 무엇을 만들고 있는지 2~3줄과 마일스톤 대비 진척. 매번 바꾸지 않는다.

**2. 현재 상태:** 지금 당장의 상태를 한 문단으로 쓴다. 앱이 실행되는지, 무엇이 진행 중인지, 막힌 게 있는지. 다음 세션이 여기만 읽어도 상황을 파악할 수 있게 쓴다. **매번 새로 쓰는 섹션이다.**

**3. 완료된 기능:** 체크리스트. 동작이 확인된 것만 적는다. "골격만 잡힘" 같은 상태는 그대로 밝힌다. 기능 단위로 쓰고, 작업 단위(커밋 단위)로 쓰지 않는다. 작업의 흐름은 5절의 몫이다.

**4. 현재 구조:** 디렉터리 트리와 각 디렉터리의 역할 한 줄. 파일을 전부 나열하지 않고 계층과 책임만 보인다.

**5. 날짜별 작업:** 이 섹션이 문서를 비대하게 만드는 주범이라서 규칙이 엄격하다.
- **날짜 하나에 항목 하나다.** 그날의 작업을 하나하나 쌓지 않는다. 그날 마지막 시점에 무엇이 달라졌는지만 요약한다.
- **같은 날 다시 갱신하면 그날 항목을 덮어쓴다.** 새 항목을 추가하지 않는다. 오전 작업과 오후 작업을 합쳐 그날의 최종 결과로 다시 쓴다.
- 최신 날짜를 맨 위에 둔다 (내림차순).
- **최근 7개 날짜까지만 남긴다.** 작업한 날 기준이고, 작업이 없던 날은 세지 않는다. 그보다 오래된 항목은 삭제한다.
- 형식:
  ```
  ### YYYY-MM-DD
  그날의 최종 결과 1~3줄. 무엇이 가능해졌거나 달라졌는지 쓴다. 과정은 쓰지 않는다.
  관련: path/to/area, 커밋 abc1234..def5678
  ```

**6. 결정사항:** 되돌리기 어렵거나, 이유를 모르면 다시 논쟁하게 될 선택이다. **결정과 이유를 함께** 쓰고, 이유 없는 결정은 적지 않는다. 형식: `YYYY-MM-DD: 결정 내용. 이유: ...`
- 결정은 날짜가 지나도 지우지 않는다. 다만 **뒤집힌 결정은 새 결정으로 교체**하고, 옛 결정은 지운다.
- 코드나 `CLAUDE.md`에 규칙으로 이미 박힌 결정은 여기서 빼도 된다.

**7. 마지막 검증:** 검증 날짜, 실행한 명령, 결과. 실패했으면 실패 내용까지 적는다. **항상 최신 1회분만 둔다.**

**8. 다음 작업 (미착수):** 우선순위 순으로 쓴다. 착수한 것은 여기서 뺀다. 막연한 아이디어가 아니라 바로 시작할 수 있는 단위로 쓴다. 10개를 넘기지 않는다.

## 정리 규칙 (갱신할 때마다 적용)

- 5절에서 7번째 날짜보다 오래된 항목을 삭제한다.
- 5절에 같은 날짜가 두 번 이상 있으면 하나로 합친다.
- 3절의 완료 항목이 너무 잘게 쪼개져 있으면 기능 단위로 묶는다.
- 6절에서 뒤집힌 결정, 이미 코드 규칙이 된 결정을 정리한다.
- 8절에서 이미 끝났거나 더는 하지 않기로 한 항목을 뺀다.
- 그래도 200줄을 넘기면, 가장 긴 섹션부터 문장을 줄인다. 2절과 8절은 줄이지 않는다.

## 템플릿

```markdown
# 프로젝트 진행 문서

> 작업 시작 전 반드시 이 문서를 먼저 읽는다. 작업 후 `progress:update` 스킬로 갱신한다.
> 날짜별 작업은 최근 7일치만 남긴다. 그 이전 기록은 git log에서 찾는다.
> 최종 갱신: YYYY-MM-DD

## 1. 프로젝트 진행사항

## 2. 현재 상태

## 3. 완료된 기능

## 4. 현재 구조

## 5. 날짜별 작업

## 6. 결정사항

## 7. 마지막 검증

## 8. 다음 작업 (미착수)
```

## 기존 문서가 다른 형식일 때

예전 형식(작업마다 번호를 매긴 로그 등)이면 처음 갱신할 때 한 번 변환한다. 같은 날짜의 항목들을 하나로 합치고, 최근 7개 날짜만 남긴다. 섹션 이름이 다르면 위 8개 섹션에 맞춘다. 변환했다는 사실을 보고에 적는다.

## 마칠 때

어느 섹션을 바꿨는지, 정리 규칙으로 무엇을 지웠는지(예: "5절 2026-09-30 이전 3개 날짜 삭제"), 검증 결과를 짧게 보고한다. 커밋은 하지 않는다.

## 하지 않을 것

- 검증하지 않은 항목을 "완료"로 기록하기
- 섹션 추가·삭제·순서 변경
- 같은 날짜에 항목을 여러 개 쌓기
- 문서 전체 재작성 (변경된 섹션만 수정한다. 형식 변환은 예외)
- 진행 문서에 코드 스니펫이나 API 명세를 길게 넣기. 그런 내용은 해당 폴더의 `CLAUDE.md`에 둔다
